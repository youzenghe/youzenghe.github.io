## Java后端（重点）

1. **自我介绍**

   **答**（模板）：基本信息（学校/专业/年级）→ 技术栈（Java 后端：SpringBoot/SpringCloud + MySQL + Redis + RabbitMQ）→ 1~2 个项目亮点（做了什么、解决了什么难点、量化结果）→ 与岗位的匹配点。控制在 1~2 分钟。

2. **除了本科课堂，还通过什么途径学习 Java？**

   **答**：系统视频课程（如黑马、尚硅谷）打基础；书籍进阶（《Java 核心技术》《深入理解 Java 虚拟机》《MySQL 实战 45 讲》）；技术社区（掘金、CSDN、美团技术团队博客）；官方文档；LeetCode 刷题；自己动手做项目并部署上线。突出「主动学习 + 动手实践」。

3. **项目是自学的，还是参与公司开发的？**

   **答**：如实回答。若是自学/课程项目，强调：需求分析、技术选型、核心模块都是自己完成，遇到 XX 问题时如何排查解决（体现独立解决问题能力）；若有实习项目则优先讲实习中自己负责的模块和贡献。

4. **JDK、JRE、JVM 的区别**

   **答**：包含关系为 **JDK ⊃ JRE ⊃ JVM**。
   - **JVM**：Java 虚拟机，负责加载并执行字节码（.class），屏蔽底层操作系统差异，是「一次编写、到处运行」跨平台能力的基础。
   - **JRE**：Java 运行环境 = JVM + Java 核心类库（如 java.lang、java.util），只能运行程序不能开发。
   - **JDK**：Java 开发工具包 = JRE + 开发工具（javac 编译器、jdb 调试器、jconsole、jstack 等）。开发用 JDK，仅运行用 JRE。

5. **volatile 了解吗？作用是什么？**

   **答**：volatile 是轻量级同步机制，两个作用：
   - **保证可见性**：一个线程修改变量后立即刷回主内存，其他线程读取时强制从主内存读（底层通过 lock 前缀指令 + 缓存一致性协议 MESI 实现）。
   - **禁止指令重排（保证有序性）**：通过内存屏障实现，典型应用是 DCL 双重检查锁单例中防止 `new` 对象「分配内存→初始化→赋值引用」被重排。
   - **不保证原子性**：所以 `volatile int i; i++` 依然线程不安全。
   - 典型场景：状态标志位（`volatile boolean running`）、DCL 单例。

6. **`++` 操作符是线程安全的吗？**

   **答**：不安全。`i++` 是「读取 → 加 1 → 写回」三步复合操作，不具备原子性。两个线程同时读到 i=5，各自加 1 后都写回 6，丢失一次更新。解决方案：
   - `AtomicInteger.incrementAndGet()`（底层 CAS 自旋，无锁高效）；
   - `synchronized` 同步块；
   - 高并发统计场景用 `LongAdder`（分段累加，减少 CAS 竞争）。

7. **如何创建一个线程？**

   **答**：常说四种方式：
   1. 继承 `Thread`，重写 `run()`；
   2. 实现 `Runnable`，传给 Thread（推荐，避免单继承限制）；
   3. 实现 `Callable<V>` + `FutureTask`（有返回值、可抛异常）；
   4. 线程池 `ThreadPoolExecutor` / `CompletableFuture`（生产推荐）。
   - 加分点：本质上真正启动线程的只有 `new Thread().start()`，其余是任务的不同封装形式；`start()` 才会开新线程，直接调 `run()` 只是普通方法调用。

8. **Runnable 和 Callable 有什么区别？**

   **答**：
   - **Runnable**：`run()` 方法，**无返回值**，**不能抛出受检异常**（只能内部 try-catch）。
   - **Callable**：`call()` 方法，**有返回值**（泛型），**可以抛异常**；配合 `Future`/`FutureTask` 通过 `get()` 获取结果（会阻塞）。
   - 线程池中 `execute()` 只接收 Runnable，`submit()` 两者都可以并返回 Future。

9. **线程池的核心参数**

   **答**：`ThreadPoolExecutor` 七大参数：
   1. `corePoolSize` 核心线程数；
   2. `maximumPoolSize` 最大线程数；
   3. `keepAliveTime` 非核心线程空闲存活时间；
   4. `unit` 时间单位；
   5. `workQueue` 任务队列（建议有界，如 ArrayBlockingQueue）;
   6. `threadFactory` 线程工厂（自定义线程名方便排查）；
   7. `handler` 拒绝策略。
   - **执行流程**：核心线程未满 → 创建核心线程；已满 → 任务入队；队列满且线程数 < max → 创建非核心线程；线程数达 max 且队列满 → 执行拒绝策略。
   - **4 种拒绝策略**：AbortPolicy（默认，抛异常）、CallerRunsPolicy（调用者线程自己执行，起到削峰反压作用）、DiscardPolicy（静默丢弃）、DiscardOldestPolicy（丢弃队首最老任务）。

10. **有了线程之后，为什么还要线程池？**

    **答**：三大好处：
    1. **降低资源消耗**：线程复用，避免频繁创建/销毁线程的开销（创建线程要分配栈内存、内核调用）；
    2. **提高响应速度**：任务到达时无需等待线程创建，直接复用空闲线程执行；
    3. **便于统一管理**：控制最大并发数防止资源耗尽，提供队列缓冲、拒绝策略、监控等治理能力。频繁 `new Thread` 在高并发下会导致线程数暴涨、频繁上下文切换甚至 OOM。

11. **线程池是怎么用的、作用/目的是什么？是提高查询速度吗？**

    **答**：这是个「纠偏题」。线程池**不能让单次查询本身变快**，它的价值是：
    - **提高吞吐量**：并发处理多个任务；
    - **并行拆分**：把一个大任务（如批量查询 / 调用多个下游接口）拆成多个子任务并行执行，用 `CompletableFuture.allOf()` 汇总，从而缩短**总耗时**（例如 3 个各 100ms 的无依赖调用，串行 300ms、并行约 100ms）；
    - **异步化**：把非核心逻辑（发短信、记日志）丢入线程池，让主流程更快返回。
    - 用法：生产中手动 `new ThreadPoolExecutor(...)`，通过 `execute/submit` 提交任务。

12. **如何确保线程安全？**

    **答**：按场景选择：
    1. **互斥同步**：`synchronized`（JVM 层，锁升级：偏向锁→轻量级→重量级）、`ReentrantLock`（可中断、可超时 tryLock、公平锁、多条件变量）；
    2. **无锁 CAS**：原子类 `AtomicInteger`/`AtomicReference`（注意 ABA 问题可用 `AtomicStampedReference`）；
    3. **线程隔离**：`ThreadLocal`（每个线程独立副本，用完必须 `remove()` 防内存泄漏）；
    4. **不可变对象**：`final`、String、不可变集合；
    5. **并发容器**：`ConcurrentHashMap`、`CopyOnWriteArrayList`、`BlockingQueue`；
    6. **volatile**：仅保证可见性/有序性的场景（状态标志）。

13. **用到哪些消息中间件（RabbitMQ）？有哪些消息模型？**

    **答**：RabbitMQ 官方 5 种常用模型：
    1. **简单队列**（一生产一消费）；
    2. **Work Queue 工作队列**（一队列多消费者竞争，能者多劳需设 prefetch=1）；
    3. **Publish/Subscribe 发布订阅**（Fanout 交换机广播）；
    4. **Routing 路由模式**（Direct 交换机按 routingKey 精确匹配）；
    5. **Topics 主题模式**（Topic 交换机通配符匹配，`*` 一个词、`#` 零或多个词）。
    - 加分：还有 RPC 模式；核心概念是 生产者 → 交换机(Exchange) → 绑定(Binding) → 队列(Queue) → 消费者。

14. **生产者广播消息，怎么设计？**

    **答**：用 **Fanout 交换机**：生产者把消息发到 fanout 类型的 Exchange（忽略 routingKey）；每个消费者各自声明一个队列并绑定到该交换机；交换机会把消息**复制**一份投递到每个绑定的队列，从而实现所有消费者都收到同一条消息的广播效果。若需要按类别选择性广播，可换 Topic 交换机。

15. **消费者是怎么获取消息的？是直接连交换机吗？**

    **答**：**不是**。消费者只与**队列**交互：交换机负责路由（本身不存消息），消息最终存储在队列中，消费者监听队列获取消息。两种方式：
    - **推模式**（常用）：`basicConsume` 注册监听，Broker 主动推送（Spring AMQP 的 `@RabbitListener`）；
    - **拉模式**：`basicGet` 主动拉取。
    - 消费后通过 ack（自动/手动）确认，手动 ack 可保证消费失败重新入队。

16. **生产者发消息到两个消息队列，消费者 1 能收到几条？**

    **答**：取决于消费者监听了几个队列。消息被路由到两个队列，相当于**每个队列各有一条独立副本**：
    - 消费者 1 只监听队列 A → 收到 **1 条**；
    - 消费者 1 同时监听队列 A 和 B → 收到 **2 条**。
    - 考点：交换机-队列-消费者的关系——同一条消息进多个队列会复制多份，队列之间互不影响；同一队列内的一条消息只会被其中一个消费者消费。

17. **一个消费者消费一条消息，怎么设计？**

    **答**：用 **Work Queue 工作队列**模式：多个消费者监听**同一个队列**，队列中每条消息只会投递给其中一个消费者（默认轮询分发）。要做到「能者多劳、处理完再拿下一条」，设置 `prefetch=1`（basicQos）+ 手动 ack：消费者未确认前 Broker 不再推送新消息。这也是横向扩容消费能力的标准做法。

18. **Spring、Spring Boot、Spring MVC、MyBatis、Spring Cloud 有哪些常用注解？**

    **答**：
    - **Spring**：`@Component/@Service/@Repository/@Controller`（声明 Bean）、`@Autowired`/`@Resource`（注入）、`@Qualifier`、`@Value`、`@Configuration`+`@Bean`、`@Scope`、`@Transactional`、`@Aspect`。
    - **Spring MVC**：`@RestController`、`@RequestMapping/@GetMapping/@PostMapping`、`@RequestParam`、`@PathVariable`、`@RequestBody/@ResponseBody`、`@RestControllerAdvice`+`@ExceptionHandler`（全局异常）。
    - **Spring Boot**：`@SpringBootApplication`、`@EnableAutoConfiguration`、`@ConfigurationProperties`、`@ConditionalOnXXX`。
    - **MyBatis**：`@Mapper`/`@MapperScan`、`@Select/@Insert/@Update/@Delete`、`@Param`、`@Results/@Result`。
    - **Spring Cloud**：`@EnableDiscoveryClient`（服务注册发现）、`@FeignClient`+`@EnableFeignClients`（远程调用）、`@LoadBalanced`（负载均衡）、`@RefreshScope`（配置热更新）、`@SentinelResource`（限流降级）。

19. **`@SpringBootApplication` 注解的作用？**

    **答**：复合注解，等于三个注解之和：
    1. `@SpringBootConfiguration`：本质是 `@Configuration`，标识这是一个配置类；
    2. `@EnableAutoConfiguration`：开启自动装配，从 `META-INF/spring.factories`（2.7+ 为 `META-INF/spring/...AutoConfiguration.imports`）加载自动配置类，按 `@ConditionalOnXXX` 条件筛选生效；
    3. `@ComponentScan`：扫描该类所在包及其子包下的组件注册为 Bean（所以启动类要放根包下）。

20. **用了微服务，Spring Cloud Alibaba 用到哪些组件？**

    **答**：
    - **Nacos**：服务注册中心 + 配置中心（临时实例 AP、持久实例 CP）；
    - **Sentinel**：流量控制、熔断降级、系统保护；
    - **Seata**：分布式事务（AT/TCC/Saga/XA 模式）；
    - **RocketMQ**：消息队列（若项目用 RabbitMQ 就说 RabbitMQ）；
    - 配合 Spring Cloud 官方组件：**Gateway**（网关）、**OpenFeign**（声明式远程调用）、**LoadBalancer**（负载均衡）。
    - 建议结合自己项目说：注册配置用 Nacos、网关用 Gateway、服务间调用用 OpenFeign、限流用 Sentinel。

21. **Gateway 的工作流程了解吗？**

    **答**：客户端请求 → **DispatcherHandler** 接收 → **RoutePredicateHandlerMapping** 根据**断言（Predicate）**匹配路由 → 交给 **FilteringWebHandler** → 依次执行**过滤器链**（GlobalFilter + GatewayFilter，按 order 排序）：
    - **pre 前置逻辑**：鉴权、限流、日志、修改请求头；
    - 通过 Netty 转发到目标服务（`lb://服务名` 时先经负载均衡从注册中心取实例）；
    - **post 后置逻辑**：修改响应、记录耗时 → 返回客户端。
    - 一句话：**断言匹配路由，过滤器链前后处理，转发目标服务**。基于 WebFlux 响应式非阻塞模型，性能好。

22. **路由转发包含哪些要素？**

    **答**：一条路由（Route）四要素：
    1. **id**：路由唯一标识；
    2. **uri**：目标地址（`http://` 直连或 `lb://服务名` 负载均衡）；
    3. **predicates 断言**：匹配条件（Path、Method、Header、Query、Time 等），决定请求是否走这条路由；
    4. **filters 过滤器**：对请求/响应做加工（StripPrefix、AddRequestHeader、限流等）。
    - 可加 order 控制多条路由的匹配优先级。

23. **Redis 有哪些基本类型？hash 怎么实现 put 操作（Redis 命令）？**

    **答**：5 种基本类型 + 常见扩展：
    - **String**（缓存对象 JSON、计数器、分布式锁）、**Hash**（对象字段级存取）、**List**（消息列表、最新列表）、**Set**（去重、共同好友交并集）、**ZSet**（排行榜、延时队列）；
    - 扩展：Bitmap（签到）、HyperLogLog（UV 统计）、GEO（附近的人）、Stream（消息队列）。
    - Hash 的 put：**`HSET key field value`**（如 `HSET user:1 name zhang age 20`，可一次设多个 field）；取值 `HGET key field`、`HGETALL key`。（HMSET 已废弃，统一用 HSET）

24. **Redis 的持久化机制？**

    **答**：两种 + 混合：
    - **RDB 快照**：把某一时刻全量数据以二进制写入 dump.rdb。`save` 阻塞主线程，`bgsave` fork 子进程写（写时复制 COW）。优点：文件紧凑、恢复快；缺点：两次快照之间的数据宕机会丢。
    - **AOF 日志**：追加记录每条写命令。刷盘策略 `appendfsync`：always（每条都刷，最安全最慢）、**everysec（默认，最多丢 1 秒）**、no（交给 OS）。文件大 → **AOF 重写**（bgrewriteaof）用最终数据生成等价最小命令集。优点：丢数据少；缺点：文件大、恢复慢。
    - **混合持久化（4.0+，推荐）**：重写时 RDB 全量做头 + 增量 AOF 追加，兼顾恢复速度和数据安全。
    - **宕机恢复**：开启 AOF 时优先加载 AOF，否则加载 RDB。

25. **MySQL 索引失效的原则？**

    **答**：常见失效场景：
    1. 联合索引**不满足最左前缀**（跳过第一列，或范围查询后的列失效）；
    2. 索引列上做**运算或函数**（`WHERE YEAR(create_time)=2024`、`id+1=10`）；
    3. **隐式类型转换**（varchar 列写 `WHERE phone = 138xxx` 数字）；
    4. **`LIKE '%xx'` 以通配符开头**（`'xx%'` 不失效）;
    5. **OR 连接了非索引列**（任一侧无索引则全表扫）；
    6. `!=`、`NOT IN`、`IS NOT NULL` 部分场景（取决于优化器成本估算）；
    7. 联表时两表**字符集/排序规则不一致**；
    8. 优化器判断**回表代价高于全表扫描**（如查询命中大部分行）时主动放弃索引。
    - 排查手段：`EXPLAIN` 看 type、key、rows、Extra。

  **答**：单机锁（synchronized/Lock）只对本进程有效，集群部署下多个实例会同时进入临界区，所以需要分布式锁。方案：
  1. **Redis**：`SET key uniqueValue NX EX 30`（原子加锁 + 过期防死锁 + 唯一值防误删，释放用 Lua 脚本判断是自己的锁再删）；生产直接用 **Redisson**（可重入、看门狗自动续期，详见下文速记 4）；

  3. **数据库**：唯一索引插入或乐观锁版本号，简单但性能差。
  - 结合项目讲场景：如「防止定时任务在多实例重复执行」「秒杀防超卖」。

### 二面

> 偏向**并发 + 分布式 + 中间件深挖**，难度高于一面：

1. **手撕：查找字符串数组的最长公共前缀**（LeetCode 14）

   **答**（纵向扫描，以第一个串为基准逐个缩短）：
   ```java
   public String longestCommonPrefix(String[] strs) {
       if (strs == null || strs.length == 0) return "";
       String prefix = strs[0];
       for (int i = 1; i < strs.length; i++) {
           // 不是公共前缀就从尾部截短，直到匹配或为空
           while (strs[i].indexOf(prefix) != 0) {
               prefix = prefix.substring(0, prefix.length() - 1);
               if (prefix.isEmpty()) return "";
           }
       }
       return prefix;
   }
   ```
   时间复杂度 O(S)（S 为所有字符总数），空间 O(1)。另一思路：横向逐字符比较所有串的第 i 位。

2. **串行优化**

   **答**（接口耗时优化思路）：
   1. **并行化**：无依赖的下游调用用线程池 + `CompletableFuture.allOf()` 并行执行，总耗时从「求和」变「取最大」；
   2. **缓存**：热点数据加 Redis/本地缓存，减少 DB 访问；
   3. **异步化**：非核心链路（通知、日志、积分）发 MQ 异步处理，主流程尽快返回；
   4. **批量化**：N 次单查合并为一次批量查询（`IN`、批量接口），减少网络往返；
   5. **SQL/索引优化**：慢查询治理；
   6. **池化**：数据库连接池、HTTP 连接池复用。
   - 注意点：并行化后要处理超时、异常隔离和线程池隔离，避免相互拖垮。

3. **线程池设计**

   **答**：从「参数怎么定 + 治理」两方面答：
   - **线程数**：CPU 密集型 ≈ N+1；IO 密集型 ≈ 2N 或按公式 `N * (1 + 等待时间/计算时间)`；最终以**压测**为准；
   - **队列**：用**有界队列**（如 ArrayBlockingQueue）防止任务堆积 OOM，容量按可容忍的延迟估算；
   - **拒绝策略**：核心业务用 CallerRunsPolicy 反压或自定义（落库/发 MQ 稍后重试），非核心可丢弃并记日志；
   - **线程工厂**：自定义线程名前缀，便于日志排查；
   - **隔离**：不同业务用独立线程池，避免相互影响；
   - **监控**：定期上报 activeCount、queueSize、completedTaskCount，支持动态调参（如美团动态线程池思路）。

4. **SQL 优化点**

   **答**：
   1. **索引层面**：为 WHERE/ORDER BY/JOIN 字段建合适索引，遵循最左前缀；用**覆盖索引**避免回表；避免索引失效写法（见合集 1 第 25 题）；
   2. **写法层面**：避免 `SELECT *`；小表驱动大表；`EXISTS`/`IN` 按内外表大小选择；深分页用**延迟关联**（先查 id 再回表）或游标（`WHERE id > lastId LIMIT n`）；
   3. **执行计划**：`EXPLAIN` 关注 type（至少 range）、key、rows、Extra（出现 Using filesort/Using temporary 要优化）；
   4. **架构层面**：大事务拆小；读写分离；冷热分离、分库分表（数据量大时）；
   5. **配置层面**：慢查询日志定位问题 SQL。

5. **Redis INCR 的业务场景**

   **答**：INCR 是原子自增，单线程模型下天然无并发问题：
   1. **计数器**：文章阅读量、点赞数、播放量；
   2. **限流**：固定窗口限流（`INCR key` + 首次 `EXPIRE`，超过阈值拒绝）；
   3. **全局唯一 ID**：批量取号段做分布式 ID；
   4. **秒杀预扣库存**：`DECR/INCR` 原子扣减，小于 0 则回滚拒绝，挡住大部分流量再落库；
   5. 统计类：接口调用次数、错误次数熔断统计。

6. **缓存一致性如何保证？**

   **答**：核心结论：**Cache Aside 旁路缓存 —— 先更新数据库，再删除缓存**，保证最终一致：
   - 为什么「删缓存」而不是「更新缓存」：避免并发写导致脏数据、避免写了但没人读的浪费；
   - 为什么「先库后缓存」：先删缓存的话，删除后-更新前的间隙里读请求会把**旧值**重新写入缓存；若必须先删，用**延迟双删**（删缓存→更新库→延迟几百 ms 再删一次）；
   - **删除失败**怎么办：重试机制（发 MQ 异步重试）或**订阅 binlog**（Canal 监听变更异步删缓存，业务解耦，最终一致的主流方案）；
   - 强一致场景：读写加分布式锁或直接读库（牺牲性能），一般业务不需要。

7. **缓存用什么数据结构？为什么？**

   **答**：
   - **本地缓存**：底层是哈希表——HashMap（单线程）/ConcurrentHashMap（并发）；成熟方案用 **Caffeine**（哈希表 + W-TinyLFU 淘汰算法，命中率高）。选哈希表因为 **O(1)** 读写；
   - **Redis 侧**：缓存对象常用 **String 存 JSON**（简单、整存整取）或 **Hash**（字段级读写、部分更新省网络和内存）；排行榜用 ZSet（跳表 + 哈希，范围查询 O(logN)）；
   - Redis 本身就是一个大哈希表（全局 dict，渐进式 rehash），这也是它快的原因之一。

8. **分布式锁选型与优势**

   **答**：三种方案对比：
   - **Redis（Redisson）**：性能最高、实现成熟（可重入、自动续期），基于内存 + Lua 原子操作；缺点：主从切换极端场景可能丢锁（可用 RedLock 缓解但成本高）。**适合高并发、短临界区、可容忍极小概率失效的业务**（大多数互联网场景选它）；
   - **ZooKeeper**：临时顺序节点 + watch 前驱，客户端宕机会话结束自动释放锁，**可靠性强、无过期时间难题**；缺点：性能低（写要过半数节点同步）。适合强一致要求场景；
   - **数据库**：唯一约束/乐观锁，实现简单无新依赖，但性能差、有死锁风险，只适合低并发。
   - 回答套路：先说项目选了 Redisson，再讲为什么（性能 + 现成解决了续期/重入/误删三大问题）。

9. **Redisson 自动续期（看门狗）**

   **答**：
   - 加锁时**不指定 leaseTime**，则默认锁过期时间 30s（`lockWatchdogTimeout`），同时启动**看门狗定时任务**：每隔 1/3（即 10s）检查一次，只要持锁线程还活着就把过期时间**重置回 30s**，防止业务没执行完锁先过期被别人抢走；
   - 一旦**显式传了 leaseTime，看门狗不启动**，到期自动释放（常见坑）；
   - 客户端宕机后没人续期，锁最多 30s 自动释放，不会死锁；
   - 底层：锁用 **Hash 结构**（field=UUID+threadId 支持可重入，value=重入次数），加解锁都是 **Lua 脚本**保证原子性。

10. **抢锁后宕机，如何保证任务执行？**

    **答**：分两层：
    - **锁不会死锁**：宕机后看门狗随进程消失，锁到达过期时间自动释放，**其他实例可以重新抢锁接着执行**——这正是「必须设置过期时间」的意义；
    - **任务不丢、不重复**：
      1. 任务设计成**幂等**（唯一业务 ID + 状态机，重复执行结果一致）；
      2. **任务状态表**记录执行进度（待执行/执行中/完成），新实例抢到锁后先查状态，从断点继续或重做；
      3. **定时任务/对账补偿**：扫描长时间处于「执行中」的任务重新调度；
      4. 若由 MQ 驱动：宕机未 ack 的消息会重新投递给其他消费者，配合幂等消费天然实现故障转移。

11. **TCC、Saga 模式**（分布式事务）

    **答**：
    - **TCC（Try-Confirm-Cancel）**：业务层面的两阶段。**Try** 预留资源（冻结库存/金额）→ 全部成功则 **Confirm** 确认扣减，任一失败则 **Cancel** 释放预留。特点：不依赖数据库锁、性能好、一致性强；缺点：**业务侵入大**（每个操作写三个方法），需处理空回滚、悬挂、幂等。适合金融扣款等短事务强一致场景。
    - **Saga**：把长事务拆成一串**本地事务** T1→T2→…→Tn，每个 Ti 配一个**补偿事务** Ci；某步失败则**逆序执行补偿** C(i-1)→…→C1。特点：无资源锁定、适合**长流程/跨系统**（如下单→扣库存→物流）；缺点：**不保证隔离性**（中间状态对外可见，需业务容忍/处理），补偿逻辑要自己写。
    - 加分对比：Seata 的 **AT 模式**（自动生成 undo log 反向补偿，侵入最小，牧原技术栈是 SpringCloud，很可能用 Seata）、2PC/XA（强一致但同步阻塞，性能差）。消息最终一致（本地消息表 + MQ）也是常用方案。

- **int 一维数组转 List**

  **答**：
  ```java
  int[] arr = {1, 2, 3};
  // 方法1：Stream（推荐）
  List<Integer> list = Arrays.stream(arr).boxed().collect(Collectors.toList());
  // 方法2：循环 add
  List<Integer> list2 = new ArrayList<>();
  for (int x : arr) list2.add(x);
  ```
  **坑点（面试官想听的）**：`Arrays.asList(arr)` 对 `int[]` **不行**——会把整个数组当成一个元素得到 `List<int[]>`，因为泛型不支持基本类型；必须先 `boxed()` 装箱。另外 `Arrays.asList` 返回的是定长视图，不能 add/remove。

- **十万个学生信息找重复**（HashSet / BitSet 判重）

  **答**：
  1. **HashSet**（通用）：遍历学生，`set.add(学号)` 返回 false 即为重复，时间 O(n)、空间 O(n)。若按对象判重需正确重写 `equals` 和 `hashCode`；
  2. **BitSet 位图**（学号是有限范围整数时更省内存）：每个学号只占 1 bit，10^7 范围仅约 1.2MB，第二次置位前发现已是 1 即重复；
  3. 数据量再大（内存放不下）：**布隆过滤器**（可能误判、适合预筛）或**分片哈希后分别判重**、或落库 `GROUP BY 学号 HAVING COUNT(*) > 1`。
  - 回答思路：先给 HashSet 通用解，再主动提 BitSet 空间优化，体现层次。

- **SpringBoot 自动配置**（自动装配原理）

  **答**：见下文速记 3。完整表述：`@SpringBootApplication` 中的 `@EnableAutoConfiguration` 通过 `@Import(AutoConfigurationImportSelector.class)` 导入选择器 → 读取所有 jar 包 `META-INF/spring.factories`（Boot 2.7+ 改为 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`）中登记的自动配置类 → 经 `@ConditionalOnClass`（类路径有该类）、`@ConditionalOnMissingBean`（用户没自己配才生效，保证用户配置优先）、`@ConditionalOnProperty` 等条件注解**过滤**，符合条件的配置类中的 `@Bean` 注入容器 → 配置值从 `application.yml` 经 `@ConfigurationProperties` 绑定。一句话：**约定大于配置，按条件把 starter 里预置的 Bean 自动注入容器**。

### （群面·集体面）

> 一个面试官对四人（2 Java + 2 前端），指定回答顺序，偏八股：

**Java 基础**

- **重载和重写的区别**

  **答**：

  - **重载 Overload**：同一个类中，方法名相同、**参数列表不同**（类型/个数/顺序），与返回值无关；编译期确定（静态多态）；
  - **重写 Override**：子类重写父类方法，**方法签名完全相同**；访问权限 ≥ 父类、抛出异常 ≤ 父类、返回值相同或为其子类（协变）；运行期确定（动态多态）。`private/static/final` 方法不能被重写。

- **`==` 和 `equals` 的区别**

  **答**：
  - `==`：基本类型比较**值**；引用类型比较**内存地址**（是否同一个对象）；
  - `equals`：Object 默认实现就是 `==`；String、Integer 等重写后比较**内容**。
  - 坑点：Integer 缓存 -128~127，`Integer a=127==b=127` 为 true，128 时为 false，所以包装类型比较一律用 equals；字符串常量池中 `"a"=="a"` 为 true 但 `new String("a")` 是新对象。

- **hashcode 的了解**

  **答**：`hashCode()` 返回对象哈希值，用于哈希容器（HashMap/HashSet）快速定位桶下标。**约定**：
  1. equals 相等的两个对象，hashCode **必须相等**；
  2. hashCode 相等，equals 不一定相等（哈希冲突）；
  3. 所以**重写 equals 必须重写 hashCode**，否则两个"相等"的对象在 HashMap 中会被放进不同的桶，出现 contains 找不到、去重失败等问题。

- **抽象类和接口的区别**

  **答**：
  - **语法**：抽象类**单继承**，可以有构造器、成员变量、具体方法；接口**多实现**，变量默认 `public static final`，JDK8 前只能有抽象方法，8+ 可有 `default`/`static` 方法，9+ 可有私有方法；
  - **设计语义**：抽象类是 **is-a**（模板复用，抽取子类公共实现，如 AbstractList）；接口是 **can-do**（能力契约，如 Comparable、Serializable）；
  - 选择：要复用代码/有状态用抽象类；只定义规范/需要多继承效果用接口。

- **ArrayList 和 LinkedList 的区别**

  **答**：
  - **ArrayList**：底层**动态数组**，支持随机访问 O(1)；中间插入删除要移动元素 O(n)；扩容为原来的 **1.5 倍**（默认容量 10，懒加载）；内存连续、缓存友好；
  - **LinkedList**：底层**双向链表**，头尾插入删除 O(1)，随机访问要遍历 O(n)；每个节点额外存前后指针，内存开销大；还实现了 Deque 可当队列/栈用；
  - 实际开发**绝大多数场景用 ArrayList**（即使頻繁尾部增删）；两者都线程不安全，并发用 `CopyOnWriteArrayList` 或 `Collections.synchronizedList`。
  - 加分：遍历中删除元素要用**迭代器的 remove()**，否则抛 `ConcurrentModificationException`（fail-fast，modCount 校验）。

**并发**

- **什么是线程安全？Java 中如何实现线程安全**

  **答**：**定义**——多个线程并发访问共享数据时，无论调度顺序如何，程序都能表现出正确的行为（结果与串行执行一致），不出现数据不一致。本质要解决三个问题：**原子性、可见性、有序性**。实现手段见合集 1 第 12 题：synchronized / Lock / CAS 原子类 / volatile / ThreadLocal / 不可变对象 / 并发容器。

- **创建线程的几种方式** → **见合集 1 第 7 题**（Thread / Runnable / Callable+FutureTask / 线程池）

- **线程池的优点** → **见合集 1 第 10 题**（降低资源消耗、提高响应速度、统一管理治理）

- **线程的死锁如何解决**

  **答**：
  - **死锁四个必要条件**：互斥、请求与保持、不可剥夺、循环等待——破坏任意一个即可预防：
    1. **按固定顺序加锁**（破坏循环等待，最常用）；
    2. `tryLock(timeout)` 获取不到就放弃并释放已持有的锁（破坏请求保持/不可剥夺）；
    3. 一次性申请所有需要的资源；
    4. 减小锁粒度、缩短持锁时间。
  - **排查**：`jstack <pid>` 会直接输出 "Found one Java-level deadlock"；或 jconsole/Arthas 检测。
  - 已发生死锁只能重启进程（Java 不会自动解除）。

**数据库**

- **MySQL 事务**

  **答**：事务是一组不可分割的 SQL 操作单元，特性 **ACID**：
  - **原子性 Atomicity**：全部成功或全部回滚，由 **undo log** 实现；
  - **一致性 Consistency**：数据从一个一致状态到另一个一致状态（其余三者共同保证的最终目的）；
  - **隔离性 Isolation**：事务间互不干扰，由**锁 + MVCC** 实现；
  - **持久性 Durability**：提交后永久生效，由 **redo log**（WAL 先写日志）实现。
  - 用法：`BEGIN; ... COMMIT/ROLLBACK;`，Spring 中 `@Transactional`。

- **事务的四种隔离级别**

  **答**（由低到高）：
  1. **读未提交 RU**：能读到未提交数据 → 有**脏读**；
  2. **读已提交 RC**：只读已提交数据，解决脏读 → 仍有**不可重复读**（同事务两次读结果不同）；Oracle/PG 默认；
  3. **可重复读 RR**：同一事务内多次读结果一致，解决不可重复读 → 理论上有**幻读**；**MySQL InnoDB 默认**，且通过 **MVCC（快照读）+ 间隙锁 Next-Key Lock（当前读）** 基本解决了幻读；
  4. **串行化**：完全串行执行，最安全性能最差。
  - 加分：MVCC 原理——undo log 版本链 + ReadView；RC 每次查询生成新 ReadView，RR 只在第一次查询生成（所以能可重复读）。

- **MySQL 索引失效的几种情况** → **见合集 1 第 25 题**

- **联表查询索引失效的情况**

  **答**：
  1. 关联字段**类型不一致**（int 关联 varchar，发生隐式转换）；
  2. 关联字段**字符集或排序规则不一致**（utf8 vs utf8mb4，函数转换导致索引失效）；
  3. **被驱动表关联字段没建索引**（JOIN 优先保证被驱动表走索引，遵循小表驱动大表）；
  4. 关联字段上使用了函数/表达式。

- **MySQL 隐式转换**

  **答**：比较双方类型不一致时 MySQL 自动转换。核心规则：**字符串与数字比较时，字符串转数字**。
  - `WHERE phone = 13800001111`（phone 是 varchar）：要把**索引列**每行的值转成数字比较 → **索引失效**，还有 `'123abc'→123` 的错误匹配风险；
  - `WHERE id = '123'`（id 是 int）：转换发生在**常量**上 → 索引不失效。
  - 结论：写 SQL 时保持类型一致，varchar 列条件永远加引号。

- **视图和存储过程**

  **答**：
  - **视图 View**：基于 SQL 查询的**虚拟表**，本身不存数据（查询时实时执行底层 SQL）。用途：简化复杂查询、权限隔离（只暴露部分列）、逻辑解耦。带聚合/子查询的复杂视图性能可能差且难优化；
  - **存储过程 Procedure**：存在数据库中的**预编译 SQL 逻辑集合**，可带参数、流程控制。优点：减少网络交互、复用；缺点：**难调试、难版本管理、数据库耦合重、水平扩展困难**——互联网公司普遍把逻辑放应用层，很少用存储过程。

**JVM / 存储引擎**

- **InnoDB 和 MyISAM 的区别**

  **答**：
  | 维度 | InnoDB | MyISAM |
  |---|---|---|
  | 事务 | ✅ 支持（ACID） | ❌ 不支持 |
  | 锁粒度 | **行级锁**（+表锁） | 只有**表锁** |
  | 外键 | 支持 | 不支持 |
  | 索引结构 | **聚簇索引**（数据即叶子节点，二级索引存主键需回表） | 非聚簇（索引与数据分离，叶子存地址） |
  | 崩溃恢复 | redo log 支持崩溃安全 | 不支持，易坏表 |
  | COUNT(*) 无条件 | 需扫描 | 直接返回存储的行数 |
  - MySQL **5.5+ 默认 InnoDB**；需要事务、并发写、高可靠 → InnoDB（绝大多数场景）；纯读、无事务的报表类才考虑 MyISAM。

- **JVM 的组成和垃圾回收算法**

  **答**：
  - **JVM 组成**：①类加载子系统（加载→验证→准备→解析→初始化，双亲委派）；②**运行时数据区**：线程私有——程序计数器、虚拟机栈（栈帧：局部变量表/操作数栈）、本地方法栈；线程共享——**堆**（新生代 Eden+2*Survivor / 老年代）、**方法区**（JDK8+ 由元空间实现，存类信息，在本地内存）；③执行引擎（解释器 + JIT 即时编译）；④本地方法接口。
  - **垃圾判定**：**可达性分析**（从 GC Roots：栈中局部变量、静态变量、常量、JNI 引用出发，不可达即垃圾）；引用计数法有循环引用问题，JVM 不采用。
  - **GC 算法**：
    1. **标记-清除**：简单但产生**内存碎片**；
    2. **标记-复制**：存活对象复制到另一半空间，无碎片但浪费空间 → 适合存活率低的**新生代**（Eden:S0:S1 = 8:1:1）；
    3. **标记-整理**：存活对象向一端移动，无碎片 → 适合**老年代**；
    4. **分代收集**：按对象存活周期分代，各代用不同算法（上面三者的组合运用）。
  - **常见收集器**：CMS（并发标记清除，低停顿但有碎片和浮动垃圾，已废弃）→ **G1**（Region 分区、可预测停顿，JDK9+ 默认）→ ZGC（亚毫秒级停顿）。

## 补充：

> 综合牛客网等平台其他牧原 Java/后端面经（数字化/智能化方向），以下题目也多次出现，一并附上答案：

### Java 基础补充

- **String、StringBuilder、StringBuffer 的区别**

  **答**：String 不可变（final char[]/byte[]，每次拼接产生新对象）；StringBuilder 可变、**非线程安全**、性能最好（单线程拼接首选）；StringBuffer 可变、方法加 synchronized **线程安全**但慢。循环拼接字符串必须用 StringBuilder，避免产生大量中间对象。

- **final 关键字**

  **答**：修饰**类**→不能被继承（String）；修饰**方法**→不能被重写；修饰**变量**→基本类型值不可变，引用类型**引用不可变但对象内容可变**。final 字段有内存语义（构造器写入对其他线程可见），常量会内联优化。

- **HashMap 底层原理（高频）**

  **答**：JDK8 中为**数组 + 链表 + 红黑树**：
  - put 流程：对 key 的 hashCode 做**扰动**（高 16 位异或低 16 位）→ `(n-1) & hash` 定位桶 → 空则直接放；冲突则链表尾插或树中插入；key 相等（hash 相等且 equals）则覆盖；
  - **树化**：链表长度 ≥ 8 且数组长度 ≥ 64 才转红黑树（否则先扩容），节点减到 6 退化回链表；
  - **扩容**：默认容量 16、负载因子 0.75，元素超过 `容量×0.75` 时扩容为 **2 倍**，元素新位置要么原下标、要么原下标+旧容量（高位 bit 决定）；
  - **1.7 vs 1.8**：1.7 头插法多线程扩容会形成**环形链表死循环**，1.8 改**尾插**；1.8 引入红黑树把最坏查询从 O(n) 降到 O(logn)；
  - HashMap 线程不安全（并发 put 丢数据）→ 并发场景用 **ConcurrentHashMap**。

- **ConcurrentHashMap 原理**

  **答**：JDK7 用 **Segment 分段锁**（默认 16 段，锁粒度大）；JDK8 抛弃分段，改为 **CAS + synchronized 锁单个桶头节点**：桶为空用 CAS 插入，不为空 synchronized 锁头节点后链表/红黑树操作，锁粒度细并发度高；扩容支持多线程协助迁移；size 用 baseCount + CounterCell 分段计数。key/value 都不允许 null。

### Spring / MyBatis 补充

- **Spring IOC 和 AOP**

  **答**：
  - **IOC 控制反转**：对象的创建和依赖关系交给容器管理，通过**依赖注入 DI**（构造器/Setter/字段）获得依赖。好处：解耦、便于测试、统一生命周期管理；
  - **AOP 面向切面**：把日志、事务、权限等**横切逻辑**从业务代码中抽离，通过动态代理织入。实现：目标类有接口用 **JDK 动态代理**，没有接口用 **CGLIB** 子类代理（Boot 默认 CGLIB）。核心概念：切点 Pointcut、通知 Advice（@Before/@After/@Around）、切面 Aspect。典型应用：`@Transactional` 声明式事务、全局日志、接口限流。

- **Spring Bean 的生命周期**

  **答**：实例化（构造器）→ 属性注入（@Autowired）→ Aware 回调（BeanNameAware/ApplicationContextAware）→ **BeanPostProcessor 前置处理** → 初始化（@PostConstruct → InitializingBean.afterPropertiesSet → init-method）→ **BeanPostProcessor 后置处理**（AOP 代理一般在这里生成）→ 使用 → 容器关闭时销毁（@PreDestroy → DisposableBean.destroy）。
  - 加分：**三级缓存解决循环依赖**——singletonObjects（成品）、earlySingletonObjects（半成品）、singletonFactories（工厂，可提前生成代理对象）；只能解决单例、Setter/字段注入的循环依赖，构造器循环依赖无解。

- **@Transactional 事务失效场景（高频坑题）**

  **答**：①方法**非 public**；②**同类内自调用**（this 调用不走代理）；③异常被 **try-catch 吞掉**；④抛**受检异常**默认不回滚（默认只回滚 RuntimeException/Error，需 `rollbackFor = Exception.class`）；⑤类没被 Spring 管理；⑥**多线程**中调用（事务基于 ThreadLocal，跨线程失效）；⑦传播行为配置错误；⑧数据库引擎不支持事务（MyISAM）。

- **MyBatis 中 `#{}` 和 `${}` 的区别**

  **答**：`#{}` 是**预编译占位符**（PreparedStatement 的 `?`），值以参数形式传入，**防 SQL 注入**，默认首选；`${}` 是**字符串直接拼接**，有注入风险，仅用于无法参数化的场景（动态表名、ORDER BY 列名），且必须用白名单校验。

### Redis / 网络 / Web 补充

- **Redis 为什么快？**

  **答**：①纯**内存**操作；②**IO 多路复用**（epoll）+ 单线程事件循环，无锁无线程切换开销（6.0 起网络 IO 可多线程，命令执行仍单线程）；③**高效数据结构**（SDS 动态字符串、跳表、压缩列表、渐进式 rehash 的哈希表）。

- **Redis 过期删除与内存淘汰**

  **答**：过期删除 = **惰性删除**（访问时检查）+ **定期删除**（周期性随机抽检）；内存满时按 `maxmemory-policy` **淘汰**：noeviction（默认，拒绝写）、allkeys-lru（最常用）、volatile-lru/ttl/random、allkeys-random、4.0+ 的 lfu 系列。

- **TCP 三次握手、四次挥手**

  **答**：**握手**：客户端 SYN → 服务端 SYN+ACK → 客户端 ACK。三次的原因：双方都确认「自己和对方的收发能力正常」，两次无法防止失效的历史连接请求（旧 SYN 迟到）建立错误连接。**挥手**：主动方 FIN → 对方 ACK →（对方数据发完）FIN → 主动方 ACK。四次因为被动方 ACK 和 FIN 分开发（收到 FIN 时可能还有数据没发完）。主动方最后进入 **TIME_WAIT 等 2MSL**：确保最后的 ACK 能重发、让旧连接报文在网络中消亡。

- **HTTP 和 HTTPS 的区别 / GET 和 POST 的区别**

  **答**：HTTP 明文、80 端口；HTTPS = HTTP + **TLS/SSL** 加密、443 端口，握手时用**非对称加密**（+CA 证书验证身份、防中间人）协商出**对称密钥**，之后用对称加密传输（性能好）。
  GET/POST：语义上 GET 获取（幂等、可缓存、参数在 URL、浏览器对 URL 有长度限制）、POST 提交（不幂等、参数在 body）；本质都是 TCP 上的 HTTP 报文，区别主要是约定。

- **Cookie、Session、Token(JWT) 的区别**

  **答**：Cookie 存**客户端**，随请求自动携带，可被篡改；Session 存**服务端**（Cookie 只存 sessionId），安全但**集群下有共享问题**（解决：Session 粘滞、Redis 集中存储）；**JWT** 无状态 token（Header.Payload.Signature，签名防篡改），服务端不存会话适合**分布式/前后端分离**，缺点是签发后**无法主动失效**（需配合 Redis 黑名单）、payload 明文可见不能放敏感信息。

- **拦截器和过滤器的区别**

  **答**：**Filter** 是 Servlet 规范，由容器管理，拦截所有请求（包括静态资源），在 DispatcherServlet **之前**执行，拿不到 Handler 信息；**Interceptor** 是 Spring MVC 机制，只拦截进入 Controller 的请求，是 Spring Bean **可注入业务对象**，提供 preHandle/postHandle/afterCompletion 三个时机。执行顺序：Filter → DispatcherServlet → Interceptor → Controller。用途：编码/跨域/全局安全用 Filter，登录校验/权限/日志埋点用 Interceptor。

- **乐观锁和悲观锁**

  **答**：**悲观锁**假设冲突一定发生，先加锁再操作：数据库 `SELECT ... FOR UPDATE`、synchronized/ReentrantLock，适合**写多**场景；**乐观锁**假设冲突少，不加锁，更新时校验：**版本号**（`UPDATE ... SET version=version+1 WHERE id=? AND version=?`，影响行数为 0 说明冲突）或 **CAS**（注意 ABA），适合**读多写少**，冲突频繁时自旋重试反而浪费 CPU。

## 高频考点参考答案速记

### 1. volatile 与 `++` 线程安全
- volatile 保证**可见性**、**禁止指令重排（有序性）**，**不保证原子性**。
- `i++` 是「读-改-写」三步复合操作，多线程下会丢失更新 → **非线程安全**。
- 原子递增用 `AtomicInteger`（CAS）或 `synchronized`。

### 2. 线程池核心参数（ThreadPoolExecutor 7 参数）
`corePoolSize`、`maximumPoolSize`、`keepAliveTime`、`unit`、`workQueue`、`threadFactory`、`handler`
- **执行流程**：核心线程未满→创建核心线程；已满→入队列；队列满且未达 max→创建非核心线程；达 max 且队列满→触发拒绝策略。
- **4 种拒绝策略**：AbortPolicy（默认抛异常）、CallerRunsPolicy（调用者执行）、DiscardPolicy（静默丢弃）、DiscardOldestPolicy（丢最老任务）。
- **参数配置**：CPU 密集型 ≈ N+1；IO 密集型 ≈ 2N+1。
- **坑**：生产建议手动 `new ThreadPoolExecutor`，避免 `Executors` 工厂方法导致 OOM；线程池 + ThreadLocal 需手动 `remove` 防内存泄漏。

### 3. SpringBoot 自动配置
- `@SpringBootApplication` = `@SpringBootConfiguration` + `@EnableAutoConfiguration` + `@ComponentScan`。
- `@EnableAutoConfiguration` → `AutoConfigurationImportSelector` → 从 `META-INF/spring.factories` 加载候选配置类。
- 通过 `@ConditionalOnXXX` 条件注解筛选生效（OnClass / OnMissingBean 等）。

### 4. Redis 分布式锁 & Redisson（二面深挖）
- 裸用 `SETNX` 有超时、续期、误删问题 → 生产用 Redisson。
- Redisson 用 **Hash 结构**存锁，field = `guid+线程ID`，value = 重入次数（实现可重入）。
- 加锁/解锁用 **Lua 脚本**保证原子性。
- **看门狗（Watch Dog）**：默认 30s 过期，未设 leaseTime 时后台定时续期；一旦显式传 leaseTime，看门狗不启动。
- 主从架构隐患 → RedLock（红锁，性能差，可容忍主从切换则用普通 RedissonLock）。

### 5. 缓存穿透 / 击穿 / 雪崩
- **穿透**：查不存在的数据 → 布隆过滤器 / 缓存空值。
- **击穿**：热点 key 过期 → 互斥锁 / 逻辑过期 / 热点永不过期。
- **雪崩**：大量 key 同时过期 → 过期时间加随机值 / 多级缓存 / 熔断降级。

### 6. 集合速记
- **重载**：同类、方法名同、参数列表不同；**重写**：子类、方法签名同，权限≥父类、异常≤父类。
- 重写 equals 必须重写 hashCode（相等对象必须有相同哈希值）。
- **ArrayList**：数组，随机访问 O(1)，中间增删 O(n)，扩容 1.5 倍（默认容量 10）。
- **LinkedList**：双向链表，头尾增删 O(1)，随机访问 O(n)。
- 遍历删除用**迭代器 remove**，否则抛 `ConcurrentModificationException`。

### 7. MySQL 索引失效常见场景
- 最左前缀不满足、索引列做运算/函数、隐式类型转换、`LIKE '%xx'` 开头、`OR` 连接非索引列、`!=` / `NOT IN` / `IS NOT NULL` 部分场景、联表字符集不一致等。
