# Day8：SQL 执行与 EXPLAIN 高频面试题

> 主题：SQL 执行与 EXPLAIN  
> 目标：能通过执行计划判断 SQL 是否可能慢，能说清“全表扫 vs 走索引”，并能落到项目优化场景。

---

## 1. 一条 SQL 从发送到 MySQL 后，大致经历了哪些步骤？

**面试官想考：** 你是不是只会背 SQL，还是理解 MySQL 执行链路。

**答题抓手：**
- 客户端发送 SQL 到 MySQL Server。
- 经过解析器做语法解析。
- 优化器选择执行计划，比如决定用哪个索引、表连接顺序。
- 执行器调用存储引擎接口读取数据。
- 存储引擎返回数据，Server 层再做过滤、排序、聚合等处理。

**项目追问：**
- 如果接口查询慢，你会从哪里开始排查？
- 为什么同一条 SQL 有时快、有时慢？

---

## 2. 你平时怎么判断一条 SQL 慢不慢？

**面试官想考：** 你有没有真实排查慢 SQL 的思路。

**答题抓手：**
- 先看接口耗时和慢查询日志，确认是不是数据库阶段慢。
- 对 SQL 执行 `EXPLAIN`，重点看 `type`、`key`、`rows`、`Extra`。
- 看是否走了合适索引，扫描行数是否过大。
- 看是否出现 `Using filesort`、`Using temporary`、全表扫描等风险。
- 结合业务数据量判断，不只看 SQL 写法。

**项目追问：**
- 如果一个接口 2 秒，其中 SQL 执行 1.5 秒，你怎么优化？

---

## 3. EXPLAIN 里你最关注哪些字段？分别怎么看？

**面试官想考：** EXPLAIN 是否真正会用。

**答题抓手：**
- `type`：访问类型，常见从好到差大致是 `const`、`ref`、`range`、`index`、`ALL`。
- `key`：实际使用的索引，如果是 `NULL`，通常说明没走索引。
- `rows`：预估扫描行数，越大越要警惕。
- `Extra`：额外信息，重点关注 `Using index`、`Using where`、`Using filesort`、`Using temporary`。

**项目追问：**
- 如果 `possible_keys` 有索引，但 `key` 是 `NULL`，可能是什么原因？
- 如果 `rows` 很大，但 `type` 不是 `ALL`，还需要优化吗？

---

## 4. EXPLAIN 里的 `type = ALL` 代表什么？一定不能接受吗？

**面试官想考：** 你是否能结合业务判断，而不是死背。

**答题抓手：**
- `ALL` 通常表示全表扫描，会扫描整张表。
- 大表、高频接口、在线业务里要重点警惕。
- 小表、配置表、一次性离线统计不一定是问题。
- 是否要优化，要结合数据量、访问频率、响应时间、并发量判断。

**项目追问：**
- 人物表、文章表、订单表这类大表出现 `ALL` 怎么处理？
- 什么场景下你能接受全表扫描？

---

## 5. `key = NULL` 一定代表没有索引吗？

**面试官想考：** 你对“有索引”和“用索引”的区别是否清楚。

**答题抓手：**
- 不一定是表上没有索引，而是优化器这次没有选择索引。
- 可能原因包括：条件字段没建索引、索引选择性太差、函数操作导致索引失效、隐式类型转换、查询返回数据比例太高。
- 优化器认为全表扫描更划算时，也可能不用索引。

**项目追问：**
- `where status = 1` 建索引一定有用吗？
- `where DATE(create_time) = ?` 为什么可能不走索引？

---

## 6. `rows` 字段很大说明什么？你会怎么处理？

**面试官想考：** 你能不能从扫描成本角度分析性能。

**答题抓手：**
- `rows` 是优化器预估要扫描的行数，不是最终返回行数。
- `rows` 很大说明过滤不够精准，I/O 和 CPU 成本可能高。
- 可以考虑补充合适索引、优化查询条件、减少返回字段、分页限制、改造业务查询方式。
- 也要配合真实执行耗时和数据分布判断。

**项目追问：**
- 列表分页越往后越慢，和扫描行数有什么关系？
- 如果人物关系查询扫描行数很大，你会考虑 MySQL 优化还是 Neo4j 承接？

---

## 7. `Using filesort` 是什么意思？一定很慢吗？

**面试官想考：** 你对排序成本和索引排序是否理解。

**答题抓手：**
- `Using filesort` 表示 MySQL 需要额外排序，不一定真的落磁盘。
- 数据量小不一定慢，但大数据量排序会明显增加成本。
- 常见优化方式：让 `where` 和 `order by` 尽量匹配联合索引，减少排序数据量。
- 不要盲目为了消灭 `Using filesort` 建很多索引，要看接口频率和数据量。

**项目追问：**
- `order by create_time desc limit 20` 应该怎么设计索引？
- 查询文章列表按发布时间倒序，为什么要关注排序字段？

---

## 8. `Using temporary` 代表什么？哪些 SQL 容易出现？

**面试官想考：** 你是否知道分组、排序、去重的代价。

**答题抓手：**
- `Using temporary` 表示 MySQL 执行过程中需要临时表。
- 常见于 `group by`、`distinct`、复杂排序、子查询或无法利用索引完成分组排序的场景。
- 临时表数据量大时，可能带来内存和磁盘开销。
- 优化方向是减少参与计算的数据量，必要时增加合适索引或改造统计逻辑。

**项目追问：**
- 统计类接口要不要实时查大表？
- 高频统计能不能用缓存、异步汇总表或定时任务？

---

## 9. `Using index` 和 `Using where` 有什么区别？

**面试官想考：** 覆盖索引和过滤逻辑。

**答题抓手：**
- `Using index` 通常表示使用了覆盖索引，可以直接从索引拿到需要字段，减少回表。
- `Using where` 表示 MySQL 还需要根据 `where` 条件继续过滤。
- 两者可能同时出现，不是互斥关系。
- 如果查询字段都在索引里，通常比还要回表更省 I/O。

**项目追问：**
- 列表页只展示 `id、title、create_time`，为什么可能适合覆盖索引？
- 为什么 `select *` 容易破坏覆盖索引？

---

## 10. 你会如何给一个慢查询设计优化方案？

**面试官想考：** 是否具备企业项目排查闭环。

**答题抓手：**
- 先确认慢在哪里：接口、网络、数据库、缓存、下游服务。
- 拿到真实 SQL 和参数，查看慢查询日志或监控。
- 用 `EXPLAIN` 看执行计划，关注是否全表扫、扫描行数、排序、临时表。
- 根据业务访问模式设计索引，不是看到字段就建索引。
- 优化 SQL 写法，避免函数操作索引列、隐式转换、无意义 `select *`。
- 压测或对比执行耗时，确认优化有效。

**项目追问：**
- 如果一个热门接口被频繁访问，除了加索引还能怎么优化？
- 数据量继续增长后，现在的索引方案会不会失效？

---

## 11. 如果 SQL 明明建了索引，为什么还是慢？

**面试官想考：** 你能不能从“走索引不等于快”继续分析。

**答题抓手：**
- 可能扫描行数仍然很大，比如索引区分度差。
- 可能需要大量回表。
- 可能排序、分组、临时表成本高。
- 可能分页偏移量太大。
- 可能锁等待、事务太长、并发竞争导致慢。
- 也可能是缓存失效或数据库资源瓶颈。

**项目追问：**
- `status` 这种低区分度字段为什么不一定适合单独建索引？
- 深分页怎么优化？

---

## 12. 项目中遇到 SQL 慢，你会怎么向面试官讲一个完整案例？

**面试官想考：** 你能不能把八股和项目经验串起来。

**答题抓手：**
- 先说业务场景：哪个接口、查什么数据、为什么高频。
- 再说问题表现：接口耗时升高、慢查询日志出现、扫描行数大。
- 接着说排查过程：抓 SQL、带参数执行 `EXPLAIN`、分析 `type/key/rows/Extra`。
- 然后说优化动作：建联合索引、改 SQL、减少字段、避免深分页、加缓存等。
- 最后说结果：扫描行数下降、响应时间下降、接口稳定性提升。

**项目追问：**
- 这个优化有没有副作用，比如写入变慢、索引占空间？

# 今日重点口述模板

如果面试官问：“你怎么看一条 SQL 有没有走索引、有没有性能问题？”

可以这样答：

> 我会先用慢查询日志或接口耗时定位到具体 SQL，然后带真实参数执行 EXPLAIN。重点看几个字段：`type` 判断访问方式，`key` 看实际用了哪个索引，`rows` 看预估扫描行数，`Extra` 看有没有 `Using filesort`、`Using temporary` 这类额外成本。如果 `type` 是 `ALL`、`key` 是 `NULL`、`rows` 很大，通常说明有全表扫描或过滤效率差的风险。然后我会结合业务数据量和访问频率判断是否需要优化，比如补联合索引、调整查询条件、减少查询字段、避免函数操作索引列，必要时加缓存或改造统计方式。
