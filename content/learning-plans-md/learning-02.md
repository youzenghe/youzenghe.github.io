# 2. MySQL 整体执行流程

## 面试题

> 说一下 MySQL 执行一条 SQL 的流程。

## 基础结构

MySQL 不是一个整体，可以分成几层：

```text
客户端
  ↓
连接层：连接管理、认证、权限、线程
  ↓
服务层：SQL 解析、语法检查、优化器、执行器
  ↓
存储引擎层：InnoDB / MyISAM / Memory 等
  ↓
内存 / 磁盘：Buffer Pool、数据页、索引页、redo、undo 等
```

## 标准回答

> 客户端发送 SQL 后，MySQL 先通过连接层建立连接并校验权限，然后服务层进行 SQL 解析、语法检查和优化器生成执行计划，执行器再调用存储引擎接口。真正的数据读写由 InnoDB 这类存储引擎完成，数据可能来自 Buffer Pool，也可能需要访问磁盘页，最后结果返回给客户端。

## 易错点

不要一上来直接背索引。

面试官问 SQL 流程时，应该先体现分层：

```text
连接层 -> 服务层 -> 存储引擎层 -> 内存 / 磁盘
```

索引是存储引擎层真正读数据时可能用到的结构，不是 SQL 执行流程的全部。

# 3. 索引到底为什么能加速

## 面试题

> 索引为什么能让查询变快？

## 核心原因

索引不是魔法，也不是缓存。

索引的本质是：

```text
有序的数据结构
```

它能加速，是因为它把：

```text
全表扫描
```

变成：

```text
树上的定位查找 + 小范围扫描
```

也就是：

```text
扫描行数少
磁盘 IO 少
排序成本可能更低
```

## 面试标准回答

> 索引是一种有序数据结构。没有索引时，MySQL 可能需要一行一行全表扫描；有索引时，可以通过 B+ 树快速定位到更小的数据范围，减少扫描行数和磁盘 IO，所以查询更快。但索引不是越多越好，因为索引会占用空间，并且插入、删除、更新数据时也要维护索引结构，会增加写入成本。

## 重要修正

今天回答里有一个小口误：

```text
索引让读写也少
```

更准确应该说：

```text
索引让查询读 IO 更少，但会增加写入维护成本。
```

## 索引不是缓存

面试官可能追问：

> 索引是不是缓存？

回答：

> 不是。索引是数据库内部维护的有序查找结构，用来缩小查找范围；缓存是把数据临时放到内存里，命中后减少访问成本。InnoDB 的 Buffer Pool 才更接近缓存，它会缓存数据页和索引页。

# 4. B 树、B+ 树、Hash 的区别

## 4.1 B 树

B 树是多路平衡查找树，不是二叉树。

特点：

```text
非叶子节点：key + data
叶子节点：key + data
查找可能在中间节点结束
叶子节点之间通常没有链表
```

问题：

```text
非叶子节点也存 data，占空间更大。
同样 16KB 的页里能放的 key 更少。
树可能更高。
磁盘 IO 可能更多。
范围查询不如 B+ 树顺。
```

## 4.2 B+ 树

B+ 树更适合数据库磁盘查询。

特点：

```text
非叶子节点：只存 key + 指针
叶子节点：存真正数据
叶子节点之间：有序链表相连
```

优势：

```text
非叶子节点不存 data，一页能放更多 key。
树更矮，磁盘 IO 更少。
所有数据都在叶子节点，查询路径更稳定。
叶子节点有链表，适合范围查询和排序。
```

比如：

```sql
where id between 100 and 200;
```

B+ 树可以先定位到 `100` 所在叶子节点，然后顺着叶子链表向后扫到 `200`。

## 4.3 Hash

Hash 索引的原理：

```text
key -> hash 函数 -> hash 值 -> 桶位置
```

优点：

```text
等值查询理论上很快。
```

缺点：

```text
没有顺序。
不支持范围查询。
不支持 order by 排序。
不支持最左前缀。
不适合 like 'abc%' 这种前缀匹配。
只适合等值查询。
```

## 面试题

> 为什么 MySQL 不直接用 Hash 索引？Hash 不是 O(1) 吗？

## 标准回答

> Hash 索引等值查询理论上很快，但它没有顺序，所以不支持范围查询、排序，也不支持联合索引的最左前缀匹配。而数据库里大量查询并不是单纯等值查询，比如 `between`、`order by`、`like '张%'`、联合索引筛选等，这些都依赖有序性。B+ 树虽然不是 O(1)，但树高很低，通常 3 到 4 层就能支撑千万级数据，并且范围扫描和排序能力更好，查询性能也更稳定，所以 InnoDB 通用索引选择 B+ 树。

补充：

> InnoDB 不是完全没有 Hash，它有自适应哈希索引，但那是内部优化，不是用户创建的通用索引。

## B 树 vs B+ 树速记

```text
B 树：
非叶子和叶子都可能存 data。

B+ 树：
只有叶子节点存 data，非叶子节点只存 key 和指针。
叶子节点之间有链表。
```

面试背诵：

> B 树和 B+ 树都是多路平衡查找树。B 树的非叶子节点和叶子节点都可以存数据，而 B+ 树只有叶子节点存数据，非叶子节点只存 key 和指针，所以同样 16KB 的页里，B+ 树能放更多 key，树更矮，磁盘 IO 更少。并且 B+ 树叶子节点之间有链表，天然适合范围查询和排序。Hash 索引等值查询快，但没有顺序，不支持范围查询、排序和最左前缀，所以 InnoDB 通用索引选择 B+ 树。

# 5. 聚簇索引、二级索引、回表、覆盖索引

## 5.1 InnoDB 的表怎么组织

InnoDB 的表本身就是按聚簇索引组织的一棵 B+ 树。

假设：

```sql
CREATE TABLE user (
    id BIGINT PRIMARY KEY,
    name VARCHAR(50),
    age INT,
    email VARCHAR(100),
    INDEX idx_name(name)
);
```

会有两类索引：

```text
主键索引 / 聚簇索引：
key = id
叶子节点 = 整行数据

普通索引 / 二级索引：
key = name
叶子节点 = name + 主键 id
```

## 5.2 为什么一张表只能有一个聚簇索引

今天容易答偏的点：

```text
聚簇索引怎么选
```

不等于：

```text
为什么只能有一个聚簇索引
```

正确原因：

> 因为聚簇索引的叶子节点存的是整行数据，InnoDB 的表数据本身就是按聚簇索引组织的一棵 B+ 树。数据只能按照一种顺序存放，所以一张表只能有一个聚簇索引。

聚簇索引选择规则：

```text
优先使用主键。
没有主键，使用第一个非空唯一索引。
还没有，就生成隐藏 ROW_ID。
```

注意：

```text
不是“第一个非重复值”，而是“第一个非空唯一索引”。
```

## 5.3 二级索引为什么不直接存整行

原因：

> 一张表可能有很多二级索引，如果每个二级索引叶子节点都存整行，会造成大量数据冗余，磁盘占用暴涨；更新一行数据时，还要同步维护很多份完整数据，写入成本非常高。所以 InnoDB 只在聚簇索引里存整行，二级索引只存索引列和主键值，需要完整数据时再用主键回表。

## 5.4 什么是回表

定义：

> 通过二级索引先查到主键 id，再用这个 id 去聚簇索引里查整行数据，这个过程叫回表。

例如只有 `idx_name(name)`：

```sql
select age
from user
where name = '张三';
```

二级索引里有：

```text
name + id
```

没有：

```text
age
```

所以要拿 `id` 回到聚簇索引查整行，这就是回表。

## 5.5 什么是覆盖索引

定义：

> 查询需要的字段，都能从某个索引里直接拿到，不需要回表，这就叫覆盖索引。

重点：

```text
覆盖索引看的是 SQL 需要的字段索引里有没有，
不是看 where 有没有用到这些字段。
```

SQL 需要的字段包括：

```text
select 字段
where 字段
order by 字段
group by 字段
```

## 5.6 典型例子

有索引：

```sql
index(name, age)
```

二级索引叶子节点可以理解为：

```text
name + age + 主键 id
```

### 例 1

```sql
select id, name
from user
where name = '张三';
```

不需要回表。

原因：

```text
id、name 都在索引里。
```

### 例 2

```sql
select id, age
from user
where name = '张三';
```

不需要回表。

原因：

```text
id、age 都在索引里。
age 没参与 where 定位，不代表 age 不能从索引里取出来。
```

### 例 3

```sql
select id, name, age
from user
where name = '张三';
```

不需要回表。

原因：

```text
id、name、age 都在 (name, age) 索引里。
```

### 例 4

```sql
select id, name, age, email
from user
where name = '张三';
```

需要回表。

原因：

```text
email 不在 (name, age) 索引里。
```

# 6. 最左前缀原则

## 6.1 本质

有联合索引：

```sql
index(a, b, c)
```

它不是给 `a`、`b`、`c` 分别建三棵树，而是按这个顺序组织一棵 B+ 树：

```text
先按 a 排序
a 相同，再按 b 排序
b 相同，再按 c 排序
```

类似字典：

```text
先按第一个字母排
第一个字母相同，再按第二个字母排
第二个字母相同，再按第三个字母排
```

所以，联合索引要从最左边开始连续匹配。

## 标准回答

> 联合索引遵循最左前缀原则，因为联合索引的 B+ 树是按索引列从左到右排序的。只有从最左列开始连续匹配，才能利用索引的有序性进行定位。如果跳过左边列，后面的列整体并不是有序的，就无法直接用于索引定位。

## 记忆口诀

```text
等值可以一路往右走。
跳列会断。
范围字段能用。
范围右边通常不能继续定位。
右边字段在索引里时，可能通过 ICP 过滤。
```

# 7. LIKE、范围查询、ICP 的综合判断

## 7.1 有联合索引 index(a, b, c)

### 题 1

```sql
where a = 1 and b = 2
```

判断：

```text
a、b 都能用于索引定位。
```

原因：

```text
从最左列 a 开始，连续命中到 b。
```

### 题 2

```sql
where b = 2 and c = 3
```

判断：

```text
不能按最左前缀利用 (a,b,c) 做有效定位。
```

原因：

```text
跳过了最左列 a。
```

严谨补充：

```text
优化器有时可能因为覆盖索引选择扫描这个索引，
但那不是高效的索引定位。
```

### 题 3

```sql
where a = 1 and c = 3
```

判断：

```text
a 能用于索引定位。
c 不能用于连续定位。
c 可能通过 ICP 在索引层过滤。
```

原因：

```text
索引按 a -> b -> c 排序。
a 固定后，数据仍然先按 b 排。
跳过 b 时，c 在整体范围内不是连续有序的。
```

### 题 4

```sql
where a = 1 and b > 10 and c = 3
```

判断：

```text
a 用于等值定位。
b 用于范围定位。
c 通常不能继续用于索引定位。
c 可能通过 ICP 过滤。
```

严谨表达：

> 联合索引遇到范围查询后，范围字段本身可以用于索引定位，但它右侧的列通常不能继续用于定位。

## 7.2 最后一组综合题

有索引：

```sql
index(a, b, c)
```

### A

```sql
where a = 1 and b = 2 and c > 3
```

判断：

```text
a、b、c 都能用于索引定位。
```

原因：

```text
c 是范围查询，但它已经是最后一列，不影响后续字段。
```

### B

```sql
where a = 1 and b like 'x%' and c = 3
```

判断：

```text
a、b 能用于索引定位。
c 通常不能继续用于定位。
c 可能通过 ICP 过滤。
```

原因：

```text
like 'x%' 是前缀匹配，可以走索引。
但它本质上类似范围扫描，所以右边的 c 通常不能继续定位。
```

### C

```sql
where a = 1 and b like '%x' and c = 3
```

判断：

```text
主要只能用 a 定位。
b like '%x' 是左模糊，不能用于索引定位。
c 因为中间断了，也不能用于定位。
b、c 在索引里时，可能做索引层过滤。
```

原因：

```text
左模糊破坏了索引的有序定位能力。
```

### D

```sql
where a > 1 and b = 2
```

判断：

```text
只能用 a 做范围定位。
b 不能继续用于定位。
```

原因：

```text
a 已经是范围查询，范围右边的 b 通常不能继续用于索引定位。
```

# 8. 今日拷打题复盘

## 题 1：MySQL 执行一条 SELECT 经过哪几层？

推荐回答：

```text
连接层 -> 服务层 -> 存储引擎层 -> 内存 / 磁盘
```

扩展：

> 客户端发起 SQL 后，连接层负责连接、认证和权限；服务层负责 SQL 解析、优化和执行计划；执行器调用存储引擎；InnoDB 再去 Buffer Pool 或磁盘页读取数据。

## 题 2：索引为什么能让查询变快？

推荐回答：

> 索引是有序数据结构，可以把全表扫描变成树上的定位查找，缩小扫描范围，减少扫描行数和磁盘 IO。

注意：

```text
不要说索引让写入也更少。
索引会增加写入维护成本。
```

## 题 3：索引是不是越多越好？

推荐回答：

> 不是。索引会占用磁盘空间，并且插入、删除、更新时要维护索引结构，索引过多会降低写入性能，还可能增加优化器选择成本。应该根据查询频率、区分度、排序分组需求和业务场景建立合适索引。

## 题 4：为什么 MySQL 不直接用 Hash？

推荐回答：

> Hash 等值查询快，但没有顺序，所以不支持范围查询、排序和最左前缀。数据库大量查询依赖有序性，B+ 树虽然不是 O(1)，但树矮、IO 少、范围查询和排序能力强，所以 InnoDB 通用索引用 B+ 树。

## 题 5：为什么一张表只能有一个聚簇索引？

推荐回答：

> 聚簇索引的叶子节点存整行数据，InnoDB 表数据本身就是按聚簇索引组织的一棵 B+ 树。数据只能按一种顺序存放，所以一张表只能有一个聚簇索引。

## 题 6：二级索引为什么不直接存整行？

推荐回答：

> 如果每个二级索引都存整行，会造成大量冗余，磁盘占用大，更新成本高。所以 InnoDB 只在聚簇索引里存整行，二级索引叶子节点存索引列和主键，需要完整字段时再回表。

## 题 7：什么是回表？

推荐回答：

> 通过二级索引先查到主键值，再拿主键去聚簇索引查整行数据，这个过程叫回表。

## 题 8：什么是覆盖索引？

推荐回答：

> 查询需要的字段都能从某个索引中直接拿到，不需要回表，这就叫覆盖索引。

关键纠正：

```text
覆盖索引不是 where 里用到了联合索引的全部字段。
覆盖索引看的是 SQL 需要的字段是否都在索引里。
```

## 题 9：有 index(name, age)，下面要不要回表？

```sql
select id, name, age
from user
where name = '张三';
```

答案：

```text
不需要回表。
```

原因：

```text
二级索引 (name, age) 里有 name、age 和主键 id。
查询字段 id、name、age 都在索引里。
```

易错点：

```text
age 没参与 where 定位，不代表 age 不能从索引里取出来。
```

# 9. 今日最终速背版

## MySQL 执行流程

> 一条 SQL 会经过连接层、服务层、存储引擎层，最后访问内存或磁盘。连接层负责连接认证，服务层负责解析和优化，执行器调用存储引擎，InnoDB 再去 Buffer Pool 或磁盘页读取数据。

## 索引本质

> 索引是有序数据结构，不是缓存。它能把全表扫描变成树上的定位查找，减少扫描行数和磁盘 IO。但索引会占空间，也会增加写入维护成本。

## B+ 树

> B+ 树非叶子节点只存 key 和指针，一页能放更多 key，树更矮，IO 更少；叶子节点存数据并用链表相连，适合范围查询和排序。

## Hash

> Hash 等值查询快，但没有顺序，不支持范围、排序和最左前缀，所以不适合做 InnoDB 通用索引。

## 聚簇索引

> InnoDB 主键索引就是聚簇索引，叶子节点存整行数据。一张表的数据只能按一种顺序存放，所以只能有一个聚簇索引。

## 二级索引

> 二级索引叶子节点存索引列和主键值，不存整行。这样能减少数据冗余和写入维护成本。

## 回表

> 通过二级索引查到主键后，再拿主键去聚簇索引查整行数据，这叫回表。

## 覆盖索引

> 查询需要的字段都在索引里，不需要回表，就是覆盖索引。判断覆盖索引看字段是否在索引中，不看这些字段是否都出现在 where 里。

## 最左前缀

> 联合索引按从左到右排序。等值条件可以一路往右匹配；跳过中间列会断；范围字段本身能用，范围右边通常不能继续用于索引定位；右边字段如果在索引中，可能通过 ICP 过滤。

## LIKE

```text
like 'x%'  可以走索引，类似范围查询。
like '%x'  左模糊，通常不能用于索引定位。
```

## ICP

> ICP 是索引下推。它不能让断掉的字段重新用于索引定位，但可以在索引扫描阶段先过滤部分数据，减少回表。
