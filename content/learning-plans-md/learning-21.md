# 2. 第一轮：EXPLAIN 与慢 SQL

## 今日提问记录

### Q1：一条 SQL 发到 MySQL 后，大概经过哪些步骤？

标准链路：

```text
客户端
-> 连接器：连接、认证、权限
-> 分析器：SQL 解析、语法检查
-> 优化器：选择索引、生成执行计划
-> 执行器：调用存储引擎接口
-> InnoDB：查 Buffer Pool / 磁盘页 / 索引页
-> 返回结果
```

注意：

```text
不要只说“服务层、校验层、存储引擎层”。
面试时要把连接器、分析器、优化器、执行器说出来。
```

### Q2：EXPLAIN 里最关注哪些字段？

重点字段：

| 字段 | 作用 |
|---|---|
| `type` | 访问方式，判断全表扫、范围扫、精准定位 |
| `key` | 实际使用的索引 |
| `key_len` | 判断联合索引用到了几列 |
| `rows` | 预估扫描行数 |
| `Extra` | 额外执行信息 |

`type` 从好到坏：

```text
system > const > eq_ref > ref > range > index > ALL
```

今日易忘点：

```text
rows 很关键，不能漏。
index 是全索引扫描，不是精准索引定位。
```

### Q3：`type = ALL` 一定要优化吗？

不一定。

可以接受的场景：

```text
小表
低频查询
离线统计
结果集占比很高
优化器认为全表扫比走索引再回表更划算
```

需要重点优化的场景：

```text
大表
高频接口
核心在线业务
rows 很大
响应时间明显变慢
```

### Q4：`possible_keys` 有值，但 `key = NULL` 说明什么？

说明表上存在候选索引，但优化器最终没有选择使用。

常见原因：

```text
索引区分度太低
返回数据比例太高
优化器认为全表扫更划算
对索引列使用函数或计算
隐式类型转换
LIKE 前模糊
OR 两边不是都有索引
字符集或排序规则不一致
```

### Q5：`Using index`、`Using filesort`、`Using temporary` 分别是什么？

| Extra | 含义 | 判断 |
|---|---|---|
| `Using index` | 覆盖索引，不需要回表 | 通常是好信号 |
| `Using filesort` | 不能直接利用索引顺序排序，需要额外排序 | 数据量大时危险 |
| `Using temporary` | 使用临时表 | 数据量大时危险 |

重点纠错：

```text
Using filesort 不是“覆盖索引没有覆盖完”。
它的核心是排序不能直接利用索引顺序。
```

可能导致 `Using filesort` 的原因：

```text
ORDER BY 字段不在索引中
ORDER BY 不满足联合索引顺序
WHERE + ORDER BY 的索引顺序不匹配
范围查询后面的排序字段用不上索引顺序
排序字段方向或顺序不匹配
```

### Q6：索引为什么能让查询变快？

面试标准回答：

> 索引是一种有序数据结构，不是缓存。没有索引时，MySQL 可能要全表扫描；有索引时，可以通过 B+Tree 从根节点一路定位到叶子节点，把全表扫描变成树上定位和小范围扫描，从而减少扫描行数和磁盘 IO。

短句背诵：

```text
索引把全表扫描变成 B+Tree 定位查找，减少扫描行数和磁盘 IO。
```

### Q7：为什么 InnoDB 常用 B+Tree，而不是 Hash 或红黑树？

B+Tree 优势：

```text
非叶子节点只存 key + 页指针，一个页能放更多 key
树高低，磁盘 IO 少
叶子节点有序并通过链表相连，适合范围查询
所有数据最终都在叶子节点，查询路径稳定
支持范围、排序、最左前缀
```

Hash 不适合作为通用索引：

```text
只擅长等值查询
不支持范围查询
不支持排序
不支持最左前缀
不适合 LIKE 'abc%' 这种前缀匹配
```

今日纠错：

```text
不要说 Hash 不支持事务。
事务是存储引擎能力，不是 Hash 数据结构本身的核心问题。
```

红黑树问题：

```text
红黑树是二叉树，数据量大时树高很高。
数据库索引存储在磁盘页里，树高高就意味着磁盘 IO 次数多。
```

# 3. 第二轮：B+Tree、聚簇索引、回表、覆盖索引

## 今日提问记录

### Q1：为什么 B+Tree 树高通常比较低？和 MySQL 页有什么关系？

核心因果链：

```text
MySQL 一个页默认 16KB
B+Tree 非叶子节点只存 key + 页指针
所以一个非叶子节点能放很多 key
分叉多
树高就低
树高低
磁盘 IO 次数少
```

今日纠错：

```text
不是“叶子节点只存字段值和主键 ID”导致树矮。
二级索引叶子节点存索引列 + 主键值；
主键索引叶子节点存整行数据；
非叶子节点主要存 key + 页指针。
```

### Q2：B+Tree 为什么适合范围查询？

标准回答：

> B+Tree 可以先通过树结构定位到范围起点所在的叶子节点，然后沿着叶子节点之间的有序链表顺序扫描，所以适合 `between`、`>`、`order by` 这类范围和排序场景。

### Q3：什么是聚簇索引？一张 InnoDB 表可以有几个？

标准回答：

> 聚簇索引是叶子节点存整行数据的索引。InnoDB 里通常主键索引就是聚簇索引。一张表只能有一个聚簇索引，因为一行数据只能按一种顺序组织。

### Q4：如果表没有主键，InnoDB 会怎么选聚簇索引？

选择顺序：

```text
1. 有主键：主键作为聚簇索引
2. 没有主键：选择第一个非空唯一索引
3. 还没有：InnoDB 生成隐藏 row_id
```

今日纠错：

```text
不是“第一个非重复字段值”。
准确说法是“第一个非空唯一索引”。
```

### Q5：什么是回表？

标准回答：

> 通过二级索引查到主键值，再拿主键值回到聚簇索引 B+Tree 查整行数据，这个过程叫回表。

流程：

```text
二级索引 B+Tree
  -> 找到主键值
  -> 回到主键索引 / 聚簇索引 B+Tree
  -> 查整行数据
```

### Q6：什么是覆盖索引？

标准回答：

> 覆盖索引不是一种新的索引类型，而是一种查询状态。只要查询需要的字段都能从某个索引里拿到，不需要回表，就叫覆盖索引。

`EXPLAIN Extra` 通常出现：

```text
Using index
```

今日纠错：

```text
覆盖索引不一定必须是联合索引。
单列索引也可能覆盖。
```

例子：

```sql
CREATE INDEX idx_name ON user(name);

SELECT name
FROM user
WHERE name = 'Tom';
```

如果只查 `name`，单列索引也可能覆盖。

再比如：

```sql
CREATE INDEX idx_name ON user(name);

SELECT id, name
FROM user
WHERE name = 'Tom';
```

在 InnoDB 中，二级索引叶子节点存 `name + 主键 id`，所以 `id、name` 都能从索引拿到，也可能覆盖。

### Q7：为什么 `select *` 容易破坏覆盖索引？

核心原因：

> `select *` 要查所有字段，而普通索引通常只包含部分字段。如果查询字段中有字段不在索引里，就必须回表查整行，所以无法覆盖。

不要说：

```text
select * 破坏了最左前缀或索引连续性。
```

覆盖索引判断的是：

```text
查询字段是否都在索引里。
```

### Q8：为什么不建议为了覆盖索引把所有字段都塞进联合索引？

原因：

```text
索引会变大，占用更多磁盘空间
写入、删除、更新时维护成本变高
页能放下的 key 变少，可能影响查询效率
优化器选择成本变复杂
```

# 4. 第三轮：联合索引、最左前缀、索引失效

假设有联合索引：

```sql
INDEX idx_abc(a, b, c)
```

## 今日提问记录

### Q1：`where a = 1`

使用情况：

```text
用到 a
```

### Q2：`where a = 1 and b = 2`

使用情况：

```text
用到 a、b
```

### Q3：`where a = 1 and b = 2 and c = 3`

使用情况：

```text
用到 a、b、c
```

原因：

```text
连续满足最左前缀，并且都是等值匹配。
```

### Q4：`where b = 2`

使用情况：

```text
通常用不到 idx_abc
```

原因：

```text
跳过了最左字段 a，不满足最左前缀。
```

### Q5：`where a = 1 and c = 3`

使用情况：

```text
a 用于索引定位
c 通常不能直接用于索引定位
c 可能通过 ICP 在存储引擎层过滤
```

重点：

```text
ICP 可以减少回表，但不代表 c 参与了索引定位。
```

### Q6：`where a = 1 and b > 2 and c = 3`

使用情况：

```text
a、b 可以用到
c 不能继续用于有序定位
```

原因：

```text
范围查询字段后面的列无法继续利用联合索引的有序性。
```

### Q7：`where a > 1 and b = 2`

使用情况：

```text
只能用 a 做范围定位
b 不能继续用于有序定位
```

### Q8：`where a = 1 order by b, c`

使用情况：

```text
a 用于过滤
b、c 可以利用联合索引顺序完成排序
```

原因：

```text
a 是等值条件。
在 a 固定的范围内，索引本来就是按 b、c 排序的。
```

### Q9：为什么 `where a = 1 and c = 3` 通常不能直接用 `c` 做索引定位？

标准回答：

> 联合索引 `(a,b,c)` 是先按 `a` 排序，`a` 相同再按 `b` 排序，`b` 相同再按 `c` 排序。跳过 `b` 后，`c` 在当前范围内不是全局有序的，不能直接用于定位，只能在已经通过 `a` 找到的范围内过滤。

### Q10：常见索引失效场景说 5 个

推荐背这几个：

```text
不满足最左前缀
范围查询后面的字段用不上
对索引列使用函数或计算
隐式类型转换
LIKE 前模糊，比如 LIKE '%abc'
OR 两边不是都有索引
索引区分度太低，优化器放弃索引
```

今日纠错：

```text
BETWEEN / IN 不要直接说成索引失效。
范围查询字段自己通常还能用索引；
失效的是范围字段后面的列。
```

# 5. 第四轮：防超卖、当前读、快照读、锁

## 今日提问记录

### Q1：为什么下单扣库存不推荐先 `select stock` 再 `update stock = stock - 1`？

错误流程：

```sql
SELECT stock
FROM product_stock
WHERE product_id = 1;

UPDATE product_stock
SET stock = stock - 1
WHERE product_id = 1;
```

并发风险：

```text
库存 stock = 1
事务 A 普通 select 读到 1
事务 B 普通 select 也读到 1
事务 A 扣减
事务 B 也扣减
如果 update 没有条件约束，就可能扣成负数
```

关键点：

> 普通 `select` 是快照读，不加锁，不能阻止其他事务修改库存。

### Q2：防超卖最核心的 SQL 怎么写？

核心 SQL：

```sql
UPDATE product_stock
SET stock = stock - 1
WHERE product_id = ?
  AND stock > 0;
```

### Q3：执行完扣库存 SQL 后，业务代码应该判断什么？

判断影响行数：

```text
affected_rows = 1：扣减成功，可以继续创建订单
affected_rows = 0：扣减失败，可能库存不足或商品不存在，不能继续创建订单
```

注意：

```text
单商品扣库存通常判断 == 1。
批量更新才可能判断 > 0。
```

### Q4：为什么 `update ... where stock > 0` 能防超卖？

标准回答：

> `UPDATE` 是当前读，会读取最新数据，并对命中的索引记录加排他锁。`stock > 0` 放在 `where` 条件里，库存判断和扣减在数据库内部一条语句中完成。并发请求同时进来时，一个事务先加锁扣减成功，另一个事务等待锁释放后会重新判断 `stock > 0`。如果库存已经是 0，影响行数就是 0，不会继续扣成负数。

并发过程：

```text
用户 A 先拿到行锁
A 读取最新 stock = 1
A 判断 stock > 0 成立
A 扣减为 0
A 提交释放锁

用户 B 等锁
B 拿到锁后重新读取最新 stock = 0
B 判断 stock > 0 不成立
B affected_rows = 0
B 返回库存不足
```

今日纠错：

```text
不是“第二个用户不能进入购买阶段”。
更准确是：第二个事务会等待锁释放，然后基于最新数据重新判断 where 条件。
```

### Q5：普通 `select` 是快照读还是当前读？会不会加锁？

普通 `select`：

```text
快照读
不加锁
读历史一致性快照
适合展示数据、列表查询
```

### Q6：`select ... for update` 是快照读还是当前读？什么时候适合用？

`select ... for update`：

```text
当前读
读取最新数据
加排他锁
```

适合场景：

```text
先读后复杂判断再更新
并且判断期间数据不能被其他事务修改
```

例子：

```sql
BEGIN;

SELECT stock, status, activity_status, limit_rule
FROM product_stock
WHERE product_id = ?
FOR UPDATE;

-- 判断库存、商品状态、活动状态、限购规则

UPDATE product_stock
SET stock = stock - 1
WHERE product_id = ?;

COMMIT;
```

### Q7：`for update` 使用时要注意哪几点？

注意事项：

```text
必须放在事务里
where 条件尽量走主键或唯一索引
事务逻辑要短
不要在事务里调用远程接口
要处理锁等待超时和死锁重试
```

今日纠错：

```text
for update 不是为了不让其他普通 select 查询到当前值。
普通 select 很多时候仍然可以通过 MVCC 读快照。
for update 的重点是阻止其他事务并发修改这行。
```

### Q8：行锁、间隙锁、临键锁分别锁什么？

| 锁 | 锁什么 | 作用 |
|---|---|---|
| Record Lock 记录锁 | 已经存在的索引记录 | 防止别人修改这条记录 |
| Gap Lock 间隙锁 | 两个索引记录之间的空隙 | 防止别人往范围里插入 |
| Next-Key Lock 临键锁 | 记录锁 + 间隙锁，左开右闭区间 | RR 下当前读防幻读 |

记忆：

```text
记录锁：锁已有记录
间隙锁：锁记录之间的空隙
临键锁：记录锁 + 间隙锁，锁一个左开右闭区间
```

重要补充：

```text
InnoDB 行锁锁的是索引记录。
如果 where 条件不走索引，可能扫描大量记录并加锁，效果上像锁表。
```

# 6. 加餐：MVCC 到底是什么

## 6.1 MVCC 是什么

MVCC 全称：

```text
Multi-Version Concurrency Control
多版本并发控制
```

一句话：

> MVCC 通过保存数据的多个历史版本，让普通 `select` 在不加锁的情况下也能读到一个一致性视图，从而提升读写并发性能。

不要把 MVCC 说成锁。

更准确：

```text
MVCC 主要服务于快照读。
锁主要服务于当前读和写操作。
```

## 6.2 为什么需要 MVCC

如果普通查询都加锁：

```text
读会阻塞写
写会阻塞读
并发性能很差
```

MVCC 的价值：

```text
普通 select 不加锁
读写可以并发
查询看到的是事务开始时或语句开始时的一致性版本
```

## 6.3 MVCC 依赖什么

InnoDB MVCC 主要依赖：

```text
隐藏字段
undo log 版本链
ReadView
```

### 隐藏字段

InnoDB 每行记录背后有隐藏信息，常见两个：

```text
trx_id：最近一次修改这行记录的事务 id
roll_pointer：指向 undo log 中旧版本记录的指针
```

### undo log 版本链

每次修改一行数据时，旧版本会写入 undo log。

多个旧版本通过 `roll_pointer` 串起来，形成版本链：

```text
当前版本
  -> 上一个旧版本
  -> 更早旧版本
  -> ...
```

### ReadView

ReadView 可以理解为：

```text
当前事务能看到哪些版本，不能看到哪些版本的判断规则。
```

普通 `select` 做快照读时，会根据 ReadView 判断版本链中哪个版本对当前事务可见。

## 6.4 RC 和 RR 下 MVCC 的区别

| 隔离级别 | ReadView 创建时机 | 表现 |
|---|---|---|
| RC 读已提交 | 每条 select 都创建新的 ReadView | 同一事务内两次 select 可能看到不同结果 |
| RR 可重复读 | 事务内第一次快照读创建 ReadView，后续复用 | 同一事务内多次 select 结果更稳定 |

简单记：

```text
RC：每次查都拍新照片
RR：事务第一次查时拍照片，后面一直看这张照片
```

## 6.5 MVCC 和锁怎么配合

```text
普通 select：快照读，走 MVCC，一般不加锁
update/delete/insert：当前读，要读最新数据并加锁
select ... for update：当前读，要读最新数据并加锁
```

面试标准回答：

> MVCC 不是锁，它主要解决普通 `select` 的一致性读问题，让读操作不阻塞写操作。当前读和写操作仍然需要锁，比如 `update`、`delete`、`select for update` 会读取最新数据并加锁。MySQL 的隔离性是 MVCC 和锁一起实现的。

# 7. 加餐：脏读、不可重复读、幻读

这三个是事务隔离级别里最常考的并发问题。

## 7.1 脏读

定义：

> 一个事务读到了另一个事务还没有提交的数据。

例子：

```text
事务 A 修改余额 100 -> 50，但还没提交
事务 B 读到了余额 50
事务 A 回滚，余额恢复 100
事务 B 刚才读到的 50 就是脏数据
```

关键词：

```text
读到了未提交数据
```

解决：

```text
RC 及以上隔离级别可以避免脏读
```

## 7.2 不可重复读

定义：

> 同一个事务内，两次读取同一行数据，结果不一样，因为中间有其他事务提交了修改。

例子：

```text
事务 A 第一次读余额 = 100
事务 B 修改余额为 80 并提交
事务 A 第二次读余额 = 80
```

关键词：

```text
同一行数据前后读到不同结果
通常是 update/delete 导致
```

解决：

```text
RR 隔离级别通过 MVCC 的一致性快照避免普通 select 的不可重复读
```

## 7.3 幻读

定义：

> 同一个事务内，两次范围查询，第二次多出了或少了符合条件的记录，像出现了幻影一样。

例子：

```text
事务 A 查询 age between 20 and 30，有 5 条
事务 B 插入一条 age = 25 的记录并提交
事务 A 再查 age between 20 and 30，变成 6 条
```

关键词：

```text
范围查询
记录数量变化
通常是 insert 导致
```

解决：

```text
普通 select 的幻读：RR 下通过 MVCC 一致性快照解决
当前读的幻读：需要间隙锁 / 临键锁阻止插入
```

## 7.4 三者对比

| 问题 | 核心 | 典型原因 |
|---|---|---|
| 脏读 | 读到别人未提交的数据 | 其他事务未提交就被读到 |
| 不可重复读 | 同一行前后读到不同值 | 其他事务 update/delete 并提交 |
| 幻读 | 范围查询前后记录数量变化 | 其他事务 insert 并提交 |

记忆：

```text
脏读：读到了还没提交的脏东西
不可重复读：同一行重复读，值变了
幻读：范围查询，行数像幻影一样变了
```

## 7.5 四种隔离级别

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---|---|---|---|
| RU 读未提交 | 可能 | 可能 | 可能 |
| RC 读已提交 | 避免 | 可能 | 可能 |
| RR 可重复读 | 避免 | 避免 | MySQL InnoDB 基本解决 |
| Serializable 串行化 | 避免 | 避免 | 避免 |

注意：

```text
SQL 标准里 RR 仍可能有幻读。
MySQL InnoDB 的 RR 通过 MVCC + 间隙锁/临键锁，基本解决幻读。
```

# 8. 今日核心纠错清单

## 8.1 EXPLAIN

```text
漏 rows 不行。
type = ALL 不一定必须优化，要看表大小、频率、rows、业务场景。
Using filesort 是额外排序，不是覆盖索引没覆盖完。
```

## 8.2 B+Tree

```text
B+Tree 树高低的原因是非叶子节点只存 key + 指针。
不要把“二级索引叶子节点存索引列 + 主键值”套到所有叶子节点上。
主键索引叶子节点存整行数据。
```

## 8.3 覆盖索引

```text
覆盖索引不是一种索引类型，而是一种查询状态。
覆盖索引不一定是联合索引，单列索引也可能覆盖。
select * 容易破坏覆盖索引，是因为查询字段通常不全在索引里，要回表。
```

## 8.4 联合索引

```text
where a=1 and c=3 只能用 a 定位，c 可能 ICP 过滤。
ICP 减少回表，但不代表 c 参与索引定位。
范围查询字段自己通常能用索引，失效的是后面的列。
IN 不要直接说成索引失效。
```

## 8.5 防超卖

```text
affected_rows = 0 不是“出现了超卖”，而是扣减失败，避免了超卖。
update 是当前读，会读最新数据并加排他锁。
后来的事务不是完全进不来，而是等待锁释放后重新判断 where 条件。
for update 不是阻止普通 select 看数据，而是阻止其他事务并发修改。
```

## 8.6 MVCC

```text
MVCC 不是锁。
MVCC 主要服务于快照读。
当前读和写操作仍然依赖锁。
RC 每条 select 创建 ReadView。
RR 第一次快照读创建 ReadView，后续复用。
```

# 9. 第二周 5 分钟口述稿

> 第二周 MySQL 我主要围绕慢 SQL、索引和防超卖来学。排查慢 SQL 时，我会先看慢查询日志或接口耗时，再用 `EXPLAIN` 看执行计划，重点看 `type、key、key_len、rows、Extra`。如果 `type = ALL`、`key = NULL`、`rows` 很大，或者 Extra 出现 `Using filesort`、`Using temporary`，就要结合数据量和访问频率判断是否优化。

> 索引本质是有序数据结构，不是缓存。InnoDB 常用 B+Tree，是因为非叶子节点只存 key 和指针，一个 16KB 页能放更多 key，树高低，磁盘 IO 少；叶子节点之间有链表，也适合范围查询和排序。InnoDB 主键索引是聚簇索引，叶子节点存整行数据；普通二级索引叶子节点存索引列和主键值。如果通过二级索引查到主键后还要回主键索引查整行，这叫回表。如果查询字段都在索引里，不需要回表，就是覆盖索引，Extra 里可能出现 `Using index`。

> 联合索引要遵守最左前缀，比如 `(a,b,c)` 可以用 `a`、`a,b`、`a,b,c`，但单独查 `b` 通常用不上。`where a=1 and c=3` 只能用 `a` 做定位，`c` 可以通过 ICP 在引擎层过滤，但不代表参与索引定位。范围查询后面的字段也不能继续用于有序定位。

> 防超卖时，我不会先 `select` 再 `update`，因为普通 select 是快照读，不加锁，并发下两个事务可能都读到库存大于 0。简单扣库存优先用一条条件更新：`update product_stock set stock = stock - 1 where product_id = ? and stock > 0`，然后判断影响行数。`affected_rows = 1` 扣减成功，`0` 就返回库存不足或扣减失败。`update` 是当前读，会读取最新数据并加排他锁，判断和扣减在一条 SQL 中完成，所以能防止扣成负数。

> 如果业务判断复杂，比如要先判断商品状态、活动状态、限购规则，就在事务里用 `select ... for update` 先锁住库存记录，再判断和更新。事务要短，条件要走索引，不要在事务里调用远程接口，并且要处理锁等待超时和死锁重试。

> MVCC 是多版本并发控制，主要服务于普通 select 的快照读。它通过隐藏字段、undo log 版本链和 ReadView，让普通查询不加锁也能读到一致性版本。当前读，比如 `update`、`delete`、`select for update`，仍然要读取最新数据并加锁。脏读是读到别人未提交的数据，不可重复读是同一行前后读到不同值，幻读是范围查询前后多出或少了记录。
