## 1. 今日主线

第 3 周的核心不是单独背概念，而是把下面这条链说顺：

```text
隔离级别
  -> 三大读问题
  -> MVCC / undo log / ReadView
  -> 快照读 / 当前读
  -> 锁 / 间隙锁 / 临键锁
  -> 防超卖
  -> 乐观锁 / 悲观锁
```

一句话总纲：

> 事务隔离级别决定并发事务之间能看到什么数据；MVCC 通过 undo log 版本链和 ReadView 实现普通 select 的一致性读；普通 select 通常是快照读，不加锁；update、delete、select for update 是当前读，读取最新版本，需要靠锁保证并发安全。

## 2. 今日暴露的薄弱点

### 2.1 术语容易说错

错误表达：

```text
Read-Write
```

正确表达：

```text
ReadView
```

ReadView 是快照读时生成的一致性视图，用来判断 undo log 版本链中哪个版本对当前事务可见。

---

### 2.2 RR 的 ReadView 创建时机要说精确

不够精确的说法：

```text
RR 第一次查询时生成 ReadView。
```

更准确的说法：

```text
RR 在事务内第一次快照读时生成 ReadView，后续普通 select 复用这个 ReadView。
```

注意：

```text
select 普通查询：通常是快照读。
select ... for update / update / delete：当前读，不走这个普通快照读逻辑。
```

---

### 2.3 for update / update 不是锁整个数据库

错误倾向：

```text
select for update 和 update 会给数据库加排他锁，阻止其他事务读写。
```

正确理解：

```text
select for update 和 update 是当前读，会读取最新版本，并对命中的索引记录加锁。
```

重点：

```text
1. InnoDB 行锁本质上锁的是索引记录。
2. 它主要阻止其他事务 update/delete 同一行，或加冲突锁。
3. 通常不会阻止普通 select，因为普通 select 可以通过 MVCC 读取历史可见版本。
4. 如果是范围条件，在 RR 下还可能涉及间隙锁或临键锁。
```

---

### 2.4 防超卖里，后来的事务不是“查不到行”

错误倾向：

```text
后来的事务查询不到数据库里的数值，所以 affected_rows = 0。
```

正确理解：

```text
行还在，只是 stock 已经变成 0。
```

两个事务同时扣最后一件库存时：

```sql
UPDATE product_stock
SET stock = stock - 1
WHERE product_id = ?
  AND stock > 0;
```

并发过程：

```text
1. 事务 A 先拿到行锁。
2. A 当前读读取最新 stock = 1。
3. A 判断 stock > 0 成立，扣减为 0。
4. A 提交并释放锁。
5. 事务 B 等待 A 释放锁。
6. B 拿到锁后重新读取最新 stock = 0。
7. B 重新判断 stock > 0，不成立。
8. B 的 affected_rows = 0，业务层返回库存不足。
```

关键句：

```text
第二个事务不是查不到行，而是等待锁释放后基于最新数据重新判断 where 条件失败。
```

---

### 2.5 间隙锁和临键锁的区间要记准

间隙锁：

```text
锁两个索引记录之间的空隙，不锁已有记录本身。
```

例子：

```text
索引里已有 10 和 20。
间隙锁可以锁住 (10, 20)。
其他事务不能插入 15。
```

临键锁：

```text
临键锁 = 记录锁 + 间隙锁。
通常是左开右闭区间。
```

例子：

```text
(10, 20]
```

表示：

```text
锁住 10 到 20 之间的间隙，也锁住 id = 20 这条索引记录。
```

今日修正点：

```text
不是左闭右开，而是通常左开右闭。
```

作用：

```text
间隙锁和临键锁主要用于 MySQL InnoDB 在 RR 下解决当前读场景的幻读问题。
```

---

### 2.6 事务里调用远程接口不等于 SSH

远程接口通常指：

```text
HTTP 接口
RPC 接口
第三方支付接口
短信接口
物流接口
调用另一个微服务
```

不建议在数据库事务里调用远程接口的原因：

```text
1. 远程调用耗时和结果不可控，可能慢、超时或失败。
2. 事务时间被拉长，数据库锁持有时间也会变长。
3. 其他事务更容易锁等待、超时，甚至出现死锁。
4. 远程接口的外部副作用通常不能随本地数据库事务一起回滚。
```

标准回答：

> 事务里不建议调用远程接口，因为远程调用耗时和结果不可控，会拉长事务时间。事务时间越长，数据库锁持有越久，越容易造成锁等待、超时和死锁。而且远程接口产生的外部副作用通常不能随本地数据库事务一起回滚，所以一致性也更难保证。

## 3. 今日拷打题与标准答案

### Q1：MVCC 是锁吗？它为什么能让普通 select 不加锁？

标准答案：

> MVCC 不是锁，而是多版本并发控制机制。数据被修改时，旧版本会进入 undo log，并通过 roll_pointer 串成版本链。普通 select 会生成 ReadView，根据事务 id 判断版本链里哪个版本对当前事务可见。因此普通 select 不需要和写操作争抢最新版本，而是读取自己应该看到的历史可见版本，所以通常不用加锁。

关键词：

```text
MVCC 不是锁
undo log 版本链
ReadView
历史可见版本
减少读写阻塞
```

---

### Q2：RC 和 RR 的 ReadView 创建时机有什么区别？

标准答案：

> RC 下每次快照读都会创建新的 ReadView，所以同一事务内后一次查询可能看到其他事务新提交的数据，因此可能出现不可重复读。RR 下事务内第一次快照读创建 ReadView，后续普通 select 复用这个 ReadView，所以普通 select 结果更稳定，可以避免不可重复读。

记忆：

```text
RC：每次 select 都拍新照片。
RR：第一次快照读拍照片，后面一直看这张照片。
```

注意：

```text
这里说的是快照读，不是当前读。
```

---

### Q3：普通 select、select for update、update 分别属于快照读还是当前读？

标准答案：

> 普通 select 在 RC/RR 下通常是快照读，通过 ReadView 和 undo log 版本链读取可见历史版本，所以一般不加锁。select for update 和 update 是当前读，它们要读取最新版本，并且后续涉及修改或防止别人修改，所以需要加锁。这个锁不是锁整个数据库，而是尽量锁命中的索引记录；如果是范围查询，在 RR 下还可能加间隙锁或临键锁防止幻读。

分类：

```text
普通 select：快照读
select ... for update：当前读
update：当前读
delete：当前读
insert：当前读相关写操作
```

---

### Q4：两个事务同时扣最后一件库存，后来的事务会发生什么？

标准答案：

> 简单扣库存可以使用 update product_stock set stock = stock - 1 where product_id = ? and stock > 0，然后判断 affected_rows。并发扣最后一件库存时，一个事务先拿到行锁并扣减成功，提交后释放锁。另一个事务会等待锁释放，随后重新读取最新数据并重新判断 stock > 0。如果库存已经是 0，where 条件不成立，affected_rows = 0，业务层返回库存不足。

关键区别：

```text
不是查不到行。
不是直接失败。
是等待锁释放后重新判断条件。
```

---

### Q5：什么时候用乐观锁，什么时候用悲观锁？

标准答案：

> 乐观锁适合读多写少、冲突概率低、可以接受失败重试的场景，常见实现是 version 字段或更新时间校验。悲观锁适合冲突概率高、数据一致性要求强、读完后还要复杂判断再更新的场景，常见实现是 select ... for update。热点秒杀场景下，大量请求可能读到同一个 version，只有少数请求更新成功，如果失败后盲目重试，会反复打到数据库，放大数据库压力。

对比：

| 维度 | 乐观锁 | 悲观锁 |
|---|---|---|
| 加锁时机 | 读时不锁，更新时校验 | 读时先加锁 |
| 适合场景 | 读多写少、冲突低 | 写冲突高、一致性强 |
| 冲突处理 | 失败、重试或返回 | 其他事务等待 |
| 风险 | 高冲突下大量失败重试 | 锁等待、死锁、吞吐下降 |

---

### Q6：为什么说 InnoDB 的行锁依赖索引？

标准答案：

> InnoDB 的行锁本质上是加在索引记录上的。where 条件命中索引时，数据库可以精准定位并锁住少量索引记录；如果 where 条件不走索引，就可能扫描并锁住大量记录，导致很多事务等待，吞吐下降，业务效果上接近锁表。

注意：

```text
不要说一定升级为表锁。
更稳的说法是：效果上接近锁表。
```

---

### Q7：间隙锁和临键锁分别锁什么？解决什么问题？

标准答案：

> 间隙锁锁两个索引记录之间的空隙，比如 (10, 20)，不锁已有记录本身，主要防止其他事务往这个范围里插入新记录。临键锁等于记录锁加间隙锁，通常是左开右闭区间，比如 (10, 20]，既锁住间隙，也锁住右边这条索引记录。它们主要用于 InnoDB 在 RR 下解决当前读场景的幻读问题。

关键词：

```text
间隙锁：锁空隙
记录锁：锁已有索引记录
临键锁：间隙锁 + 记录锁
当前读防幻读
```

---

### Q8：为什么事务里不建议调用远程接口？

标准答案：

> 事务里不建议调用远程接口，因为远程调用耗时和结果不可控，会拉长事务时间。事务时间越长，数据库锁持有越久，越容易造成锁等待、超时和死锁。而且远程接口产生的外部副作用通常不能随本地数据库事务一起回滚，所以一致性也更难保证。

例子：

```text
下单事务中调用支付接口。
本地订单事务后续回滚了，但支付接口可能已经扣款。
这类外部副作用不能靠本地数据库 rollback 自动撤销。
```

## 4. 睡前最小背诵版

今晚只背下面这些：

```text
1. MVCC 不是锁，它通过 undo log 版本链和 ReadView 实现普通 select 的一致性读。
2. undo log 用于事务回滚和 MVCC 历史版本，redo log 用于宕机恢复。
3. RC 每次快照读创建新 ReadView，RR 第一次快照读创建后复用。
4. 普通 select 是快照读，select for update / update / delete 是当前读。
5. 当前读读最新版本，所以要加锁；普通 select 通常靠 MVCC，不加锁。
6. 防超卖优先用 update ... where stock > 0，并判断 affected_rows。
7. 两个事务扣最后一件库存，后来的事务等待锁释放后重新判断 stock > 0，失败则 affected_rows = 0。
8. InnoDB 行锁锁的是索引记录，不走索引可能锁很多行，效果上接近锁表。
9. 间隙锁锁空隙，临键锁 = 间隙锁 + 记录锁，通常左开右闭。
10. 事务里别调远程接口，因为会拉长锁持有时间，而且外部副作用不能自动回滚。
```

## 5. 明天优先复习顺序

```text
1. MVCC 主线：MVCC -> undo log -> 版本链 -> ReadView。
2. ReadView 时机：RC 每次快照读创建，RR 第一次快照读创建后复用。
3. 快照读 / 当前读：普通 select vs select for update / update。
4. 锁：行锁依赖索引，记录锁、间隙锁、临键锁。
5. 防超卖：条件更新 + affected_rows。
6. 乐观锁 / 悲观锁：适用场景与热点秒杀重试风险。
```
